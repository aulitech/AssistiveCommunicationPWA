# Peri

Assistive communication driven entirely by gaze and dwell. React + Vite + Tailwind CSS, deployed to Netlify as an installable PWA.

## Development server

`pnpm dev` starts Vite on http://localhost:5173 with hot reload. `pnpm build` writes `dist/`, and `pnpm preview` serves that build. `pnpm probe` opens the pointer probe — see `tools/` below.

Nothing starts a server for you — this project was scaffolded by Figma Make and no longer is, so there is no harness running one in the background.

## Project Structure

This is the canonical project structure. Start with task-relevant files below. Only follow imports or inspect other files when required, when a documented path is missing, or when the repository contradicts this guide.

`src/` is **layered, lowest first**. A directory may import from itself and from anything on an earlier line, never from a later one. `tests/app/structure.test.ts` fails the build if that is broken, so the rule is enforced rather than merely described.

| Layer | Directory | Holds |
|---|---|---|
| 1 | `core/` | What Peri knows and keeps. No React, no network, no screens |
| 2 | `ui/` | The controls and contexts every screen is built from |
| 3 | `translate/` | Words into other words, which has to happen before anything says them |
| 4 | `voice/` `sync/` `listen/` | The three that talk to something outside this device |
| 5 | `menu/` | The panel that slides down, and everything reached from it |
| 6 | `talk/` `signin/` `legal/` | The three screens |
| 7 | *(root)* | `App.tsx`, `main.tsx`, and the tests that drive the whole app |

**core/** — readable on its own; nothing else in `src` is needed to follow it

- `core/phrases.ts` - Parses `core/imports/phrasetable.json` into phrases, including the fill-in-the-blank slots, their `aliases` lookups, the user's own lists that fill `{contact}` and `{name}`, and the fixed emergency phrases
- `core/store.ts` - Everything the app persists and the shapes it persists it in: settings, the phrase store, the alias lists, the signed-in user, the linked account, the sent messages, how much each phrase is used, the last category and voice used, the `localStorage` keys, **whose board they are read from** — see *Whose board* — and the pure operations that arrange the category tabs and the emergency bar
- `core/backup.ts` - The export/import file format under **Menu → Backup & sharing**: building one, reading one back, and applying it
- `core/sheet.ts` - **The board as a spreadsheet**, and a spreadsheet back onto the board — see *The board as a spreadsheet*. Rows out, CSV and tab-separated text in and out, `applySheet`, which is to a sheet what `applyBackup` is to a backup — rows in, a store out, nothing touched — and `applyLists`, the same for the word lists that ride after the phrases
- `core/xlsx.ts` - An Excel workbook in and out, as a table of text, **written by hand** — a zip of a few XML files, stored on the way out and inflated by the browser's own `DecompressionStream` on the way in. Every cell written is text; every cell read is the text it shows, whoever wrote the file
- `core/virtual.ts` - How much of the grid to render, and when to render more
- `core/search.ts` - Narrowing the grid to what is being typed. Ranks a whole-phrase prefix first, then a word prefix, then the letters used as initials — which is what lets "ttyl" find "Talk to you later". Matched against the words rather than the markup, so `**Help** me` is found by typing "help"
- `core/sort.ts` - **What order the grid is in** — see *Ordering the grid*. The four arrangements and the arithmetic behind them, including the one the user builds by hand. It runs *before* `search`, never after: filtering to a category cannot reorder and the ranking is a stable sort, so arranging first lets the chosen order decide ties within a rank band while a typed word still puts the best match first
- `core/markdown.ts` - The markup a phrase may carry, and taking it back off. `layout` for drawing, `stripMarkdown` for everything a phrase is *not* drawn into — spoken, searched, announced
- `core/links.ts` - Reading a URL and a label out of a paste or a drop, and writing them as `[label](url)`. A clipboard and a drag carry the same shape, so one reader serves both
- `core/translation.ts` - What a phrase says in another language, looked up **synchronously** — see **Speaking another language**. Two sources: the tables Peri ships, lazily loaded for whichever language is chosen, and whatever has been translated on this board before
- `core/report.ts` - `reportFailure`, one shape for every service failure that reaches the console — see **Saying when something failed**
- `core/keys.ts` - **The keys Peri draws for itself**, as two layers of three rows — see **Peri's own keyboard**
- `core/prose.ts` - The blocks long-form text is written in, and `prosePieces`, which breaks a line into words and the icons it names. **A guide that names a button has to show it**: every control here is a glyph and nothing else, so "rest on the speaker button" asks somebody to match a description against a picture, which is what this app's readers are least able to do quickly. The mark is `:speak:` — **colons rather than braces**, which is the one shape this text cannot use, since the guide teaches `{pronouns}` as the syntax for a phrase's own choices and a brace-delimited mark would have eaten the very words explaining it
- `core/crypto.ts` - Locking a board before it leaves the device. One passphrase derives two things through HKDF off a single PBKDF2 run: the AES-GCM key the board is sealed with, and **the address it is stored under**. The account is the salt
- `core/envelope.ts` - The wire format alone: the envelope, its parser, the address and the revision. **It imports nothing, and that is load-bearing** — the Netlify function takes this and nothing else out of `src`, so both ends validate identically. One value taken from the store once pulled `core/phrases` in behind it and turned a 3KB Lambda into 418KB of phrase table
- `core/version.ts` - `APP_VERSION`, which release this is — see *Versioning*. Written in `package.json` and put into the bundle by `vite.config.ts`
- `core/sync.ts` - Everything else about what travels and which way: the snapshot, `decideSync`, `hasOwnBoard`, `portableSettings`, and the wire format passed straight back out so a caller needs one import

**ui/** — the shared vocabulary

- `ui/dwell.ts` - `useDwellControl`, the hover-and-hold primitive every control is built on. `onDwellActivation` is the other half of it — one listener set told *before* any control fires, for the things that mark what just happened and have to stop claiming it the moment anything else does. `repeatMs` is what makes a control repeat while it is held; every caller passes `settings.repeatDelayMs` rather than a number of its own. `holdDwells` is the app going deaf for a second because the screen moved under the pointer — see **Settling after the screen moves**. It also watches the pointer's own stream, because one browser says nothing at all when the pointer leaves — see **When the pointer leaves without saying so**
- `ui/caret.ts` - `useCaretDwell`, the hold that puts the caret under the pointer, and `caretIndexAt`, which asks the browser what character sits there. A text box was the one control dwell alone could not drive: hovering can focus it, but the caret only ever moved on a click. There is one box now and it does two jobs — the message being composed, and, in edit mode, the phrase being written — so the hook settles the awkward parts once for both
- `ui/link-input.ts` - `useLinkInput`, the paste and drop handlers a text box needs to turn a link into markdown, and `pasteFromClipboard` behind the **paste control** in the topbar. One box, so one paste, into whichever of the two it is holding
- `ui/typing.ts` - Writing into whatever field has the caret. **The value has to go through the prototype's own setter**: React keeps a tracker of the last value it wrote, and a plain `field.value = …` slips past it — the `input` event fires, React finds no change against what it believes is there, and drops it. The letter appears and is gone at the next render, with the app still holding the old text. `tests/ui/typing.test.tsx` asserts against React's state rather than the node, or it would pass either way
- `ui/keyboard.tsx` - The keyboard itself: ninety-odd dwell keys, shift as a ring, and a symbol layer. It types into the focused field rather than into any box it knows about, which is what lets one keyboard serve every field in the app
- `ui/reorder.ts` - `useReorder`, the pick-up-and-put-down primitive behind both bars that can be arranged. A pointer-drag needs a button held down while the pointer moves, which is the one gesture a dwell user cannot make — so anything arrangeable can also be *lifted*: one dwell picks it up, a second on another drops it there. The category tabs and the emergency bar arrange by identical rules, so the rules are written once here
- `ui/controls.tsx` - The dwell controls more than one screen uses: `DwellButton`, `NavItem`, `SettingRow`, `SettingSpinner`, `ScrollRow` (a row that scrolls sideways with its own dwell arrows — the filter chips outgrow the screen), `PickerModal`, `PickerTile` and `PickerTrigger` (a full-screen grid of choices and the control that opens it — a dwell rather than a `<select>`, since an operating system draws a native list outside the page where nothing can be hovered; portalled to the body — a panel animated with `transform` makes `position: fixed` resolve against the panel rather than the viewport), `ScrollPane` (four dwell controls — jump to top, nudge up, nudge down, jump to bottom — in **a rail down the pane's right edge**, the grid's rail in every particular a gaze learns by: the same 44px, the same edge, the four sharing the height, the same fill rising from the bottom. One edge for everything that scrolls. The rail appears only when there is somewhere to go at all, so a pane that fits keeps its width, but then **all four, always**, the ones with nowhere to go inert in their place — they share the rail's height, and one that came and went would stretch the others into its space under a resting pointer. They were bars above and below the content, which cost a short screen two strips of height and put the controls somewhere different from the grid's), `PanelButton`, `ProseSections`, `DwellCursor`, `BusyIndicator` (the one thing on screen that says *wait* — see **Waiting**), and the four that exist so **nothing in the app answers only to a press** — see *Everything a dwell can reach*: `DwellInput` (every single-line field), `DwellLink` (every link), `BoxScroll` (the arrows inside a text box that has more in it than shows), and `FileButton` (every file chooser — a dwell control in front of the one bare input in the app, which says when the browser refuses a rest)
- `ui/settings.ts`, `ui/edit-mode.ts` - The two React contexts. Separate from the panels that edit them, or `controls.tsx` would have to import the settings screen, which is built out of `controls.tsx`
- `ui/style.ts` - `cx` and `dwellVar`. Not components, so not in `controls.tsx` — a module mixing the two loses fast refresh for everything importing it
- `ui/prose-icons.tsx` - Which icon each name in a line of prose draws. A lookup table rather than a component, so it is not in `controls.tsx` — and `tests/app/structure.test.ts` holds every name the guide and the legal pages use to this list, because a mark nothing defines draws nothing: the sentence keeps its spacing and quietly loses the thing it was pointing at
- `ui/pending-choice.ts` - `usePendingChoice`, **a grid with Done and Cancel on it waits for one of them**. A tile marks a choice; Done writes it, Cancel throws it away, and nothing about the board changes before either. Three grids — the spoken language, the reply model, the phrase order — closed on the first tile a rest landed on, with a Cancel that did what Done did; a rest is how somebody *looks* at a tile as well as how they choose one, so a grid committing to the first tile the eye passes over chooses for them. **Held rather than applied and put back**, because choosing a language writes down the voice it is leaving and one only passed over must not leave a voice behind. **Done with nothing moved writes nothing**, which is not an economy: the same language chosen again still writes to the voice memory, and a settings change travels to the other devices as a notice about something nobody did. The voice picker applies as it goes and puts back on Cancel instead, deliberately — every voice speaks as it is chosen, and hearing it is the point
- `ui/scroll-edges.ts` - `useScrollEdges`, whether something that scrolls has anywhere left to go and the moves a dwell can make on it. One answer for `ScrollPane` and for the two text boxes, which scroll themselves and so cannot be wrapped in a pane. `mounted` re-attaches it to an element that is not always there — the heard box exists only while listen mode is open
- `ui/units.ts` - `seconds`, how a time is written: in seconds, with **three figures after the point or none**, never one or two — `1s`, `0.800s`, `1.050s`. The auto-repeat row said `1000ms` under two dwell rows saying `1.5s`; three figures because the repeat steps in fifty milliseconds and one would write `1050` as `1.1s`, a value that spinner cannot hold
- `ui/settle.ts` - `useSettled`, the quarter-second an indicator waits before saying anything. Its own module for the reason `style.ts` is: two things reach for it now — the `BusyIndicator` in the corner and the line that waits in the message box for a reply — and a hook exported from `controls.tsx` would cost fast refresh to nearly every screen here
- `ui/icons.tsx` - Inline SVG. Icons used by exactly one screen stay with that screen — `ReorderIcon` is here because both bars that can be arranged draw it, `PageIcon` because both bars that can be paged do, and `SortAlphaIcon`/`CustomOrderIcon` because the category bar and the Aliases panel both offer the same two arrangements

**translate/**

- `translate/client.ts` - Google Cloud Translation, for the phrases Peri ships no translation for. **It unescapes what comes back**: Google escapes its answer even when plain text is asked for, and `I&#39;m cold` handed to a synthesiser is read out as "I ampersand hash thirty-nine m cold". Decoded by hand rather than through `innerHTML` — this string goes to a speech engine and a clipboard, and parsing it as markup is how somebody else's board becomes a way of running their script. **Nothing throws** — failing to translate is not failing to speak, so every failure is a value and the caller says the words as they were written

**voice/**

- `voice/speech.ts` - The single place utterances are created, and the routing between the device voice and a linked account
- `voice/audio-cache.ts` - Audio already **paid for**, in three layers — see *Not paying for a clip twice*. Memory answers synchronously, which is what makes a phrase's own voice usable on the emergency bar; IndexedDB, one database for each board, is what stops a reload buying the board again; and the third is the user's other devices, **installed from above** rather than imported, since the module that reaches them sits beside this one in the layering
- `voice/picker.tsx` - Choosing a voice. One control, used by Settings for the app's voice and by the edit strip for a single phrase's. It sits above `ui/` in the layering for that reason — it is built out of `ui` controls, so `voice` cannot be beside it
- `voice/groups.ts` - Cutting a long voice list down: device voices by language, an account's by the collection it files them under. `speechLanguages` is the same question asked the other way round — which languages this device can speak at all, which is what the **Spoken language** setting offers. `offeredLanguages` and `languageLabel` sit here rather than beside the picker that draws them, because a module mixing components with plain functions loses fast refresh for everything importing it
- `voice/language-picker.tsx` - Choosing the language the board is spoken in. Beside `VoicePicker` and shaped like it, because the two are asked together now that a voice is remembered per language — and because the settings panel and the topbar both offer them, and two copies of a language list would be two chances to disagree about what the board speaks
- `voice/elevenlabs.ts` - A linked ElevenLabs account: validating a key, fetching its voices, fetching audio, and the cache in front of it

**listen/** — the other half of the conversation

- `listen/recognition.ts` - The microphone, and the words it hears — see *Listen mode*. **This is the browser's ear, not ours**: `SpeechRecognition` is a platform API and most browsers send the audio to a speech service of their own rather than recognising it on the device. That is a disclosure rather than a detail. Both names are asked for, prefixed and not, and a browser with neither is answered by `canListen` before the control is ever drawn
- `listen/apology.ts` - **What the board says out loud while a reply is being written** — see *Filling the silence*. The shipped apologies, which are the answer whenever there is nothing else; which one gets said; and asking Anthropic for more, in a request that carries nothing of anybody's
- `listen/suggest.ts` - Suggested answers to a question that was heard, up to twenty of them. **The riskiest thing in this app**, and the one rule everything is arranged around is that **a suggestion is never spoken** — they land on the board as cells to choose between, the one chosen goes into the message box, and it is said only when the person dwells on Speak, like any other message. The key is the user's own, for the reason the ElevenLabs key is: it bills them for something they chose, and unlike the translation key it cannot be made safe to inline, since nothing restricts an Anthropic key to one site

**sync/**

- `sync/audio.ts` - ElevenLabs clips on the server, one blob each — see *Not paying for a clip twice*. Not part of the board and deliberately so: audio is bought by speaking rather than by editing, and folding it into the board would make saying a phrase look like an edit. A clip's address is **derived from the words and the voice**, so a second device works it out for itself and there is nothing to look up; the one thing that *is* listed is what has been uploaded, so *Stop and erase the copy* can take the audio too
- `sync/client.ts` - The four calls to `/api/sync`. **An answer that is not JSON is refused**, because a missing endpoint here is not a 404: the SPA catch-all rewrites it to the app, so the answer is 200 with HTML in it and a client trusting `res.ok` crashes on the first `{` it cannot find. **Nothing throws** — a board works offline, and a device that cannot reach the server has lost nothing at all, so every failure is a value and the worst case is a line of text under a setting
- `sync/use-sync.ts` - The hook that decides when: on arrival, a debounced moment after any change, on the tab being looked at again, on the network coming back, and a slow beat behind all of it

**menu/**

- `menu/menu.tsx` - The panel itself, the four things it opens, and the confirmation in front of **Sign out**. Its top line is three columns — who is signed in, the name and version centred, and Back — and **Back's column is never narrower than Back**, so on a phone at a large text size the name gives way rather than the title being laid over the only way out. **A nav item is only as wide as what is written on it** — stretched to the panel, which spans the viewport, each row answered to a gaze anywhere along a metre of empty space beside it, and the five tiled the panel with no gap between one and the next. **The menu is deaf for a second after one of them closes** (`REOPEN_GUARD_MS`): a pointer rests where it last fired, so Back and the sign-out dialog's buttons are both sitting over the menu that comes back, and an item arriving under a pointer already at rest opens on its own. Nothing about the items changes while the guard is up — five rows greying out and coming back reads as a fault rather than as a pause — so the cue is simply that the fill does not start — the one item here that empties the screen. That dialog is portalled and centred on purpose: a pointer rests where it last fired, so a "yes" appearing under the nav item would be answered by the pointer already sitting there. **Back is the only way out that does not need a keyboard** — the scrim behind the panel is inert on purpose, since a pointer wandering across it used to take the menu away
- `menu/settings-panel.tsx`, `menu/aliases-panel.tsx`, `menu/backup-panel.tsx`, `menu/help-panel.tsx` - Those four. All four panels bound their height and scroll — Aliases grows with every word, the settings with the linked-account row — and hold their content to the same 68ch column: the panel spans the whole viewport, so without it a setting's label sits at one edge of a wide monitor and its control at the other. The voice picker and the backup category picker are both full-screen grids built from `PickerModal` — the first single-select, the second multi-select. The voice picker is a full-screen grid, and choosing a voice speaks a sample in it and leaves the grid open — a preview button beside each of sixty tiles would put two targets in every one. Cancel puts back the voice the picker opened on, which is what makes trying them free. It is portalled to the body: the panel is animated with `transform`, and a transformed ancestor makes `position: fixed` resolve against that ancestor rather than the viewport — any full-screen overlay opened from inside a panel needs the same treatment
- `menu/sheet-section.tsx` - The spreadsheet half of **Backup & sharing**: three ways out (Save for Excel, Save as CSV, Copy for Sheets) and two back in (Choose a spreadsheet, Paste from Sheets), and the line saying what a sheet will change — to the phrases and to the word lists — before anything does
- `menu/backup-file.ts` - Turning a backup, or the board as a spreadsheet, into a file the browser saves — `saveFile`, which both use. Out of `core/backup.ts`, which touches nothing, and out of the panel, because two places offer to save one: **Backup & sharing**, and the confirmation in front of a factory reset
**Settings, the guide and Backup & sharing fill the viewport**; the menu itself and Aliases hang down only as far as their content. Backup was held to half the screen until the spreadsheet went under it, which left most of its controls a dozen dwells on an arrow away below a panel that stopped halfway down an empty screen. `.top-panel.is-tall`, set from `TALL_VIEWS` in `menu.tsx`, sized in `dvh` — on a phone `vh` is the viewport with the browser chrome *hidden*, so a panel sized in it runs under the address bar and its last row cannot be reached.

- `menu/help.ts` - The guide, as data. **Its headings fold up**, one open at a time, first open on arrival — fifteen sections is a lot to scroll past by dwell to reach the one you came for. Folded, it is a list, so the headings carry no padding: the tighter the list the more of it is on screen, which is the point of folding it. **Opening one scrolls it to the top of the pane**, in an effect after the render that opened it, so what was just chosen is the first thing on screen; closing does not scroll, since closing is not going anywhere. The legal pages are the same shape of text drawn by the same `ProseSections`, and deliberately do *not* fold: they are documents, served at their own URLs and indexed

**talk/** — **the usual starting point for UI work**

- `talk/talk.tsx` - The screen: which category is showing, which mode is on, and what to say when an operation finishes
- `talk/use-board.ts` - What is on the board and every way of changing it
- `talk/use-composer.ts` - The message being built: its text, its history, and the caret
- `talk/use-editor.ts` - The phrase being written or reworded, which in edit mode is what the message box holds. There is **always a draft** — choosing a phrase points it at one, and nothing opens or closes. Only the fields actually touched are kept; the rest are derived from the phrase each render, so a draft cannot go stale against a store that changed underneath it. `open` is stable across renders on purpose: it reaches every one of a couple of thousand memoised phrase cells
- `talk/use-sent.ts` - The messages already spoken or copied
- `talk/use-translated.ts` - What has been said in another language — see *The Translations tab*. The Sent list's twin, and built to the same shape for the same reasons: a record of what somebody actually said rather than anything they made, so its own key, never in a backup, and not a category
- `talk/use-apologies.ts` - The five apologies the board keeps ready, topped up after one is said and at no other time — see *Filling the silence*
- `talk/use-usage.ts` - How much each phrase is used. Every phrase chosen is counted as it is chosen; **what the board is ordered by is a copy of that record, taken when somebody last changed what they were looking at** — see *Ordering the grid*
- `talk/use-listen.ts` - Listen mode: the microphone, what was heard, what it means, and the reply offered for it. Three services behind one box, and each failing costs only itself
- `talk/suggestions.ts` - The answers offered to a question, as cells on the board. **A suggestion is a phrase or it is nothing**: drawing a blank as a dashed gap, landing the caret in it, narrowing to a typed word and reading the words to a screen reader are all work `Phrase` does, so the answers become phrases here rather than a kind of their own. A gap is a slot with no options — the app's own blank — rather than three underscores drawn on a cell, and the ids carry the question they answer so a new question draws new cells
- `talk/heard.tsx` - The box above the message. A second text area and deliberately not a second message: the question is somebody else's words and the answer is the user's
- `talk/use-toast.ts` - The line that appears and fades
- `talk/grid.tsx` - The grid, the cell, the mark on the last phrase said, and the rail. The rail is five ways of moving through the grid and, ruled off above them, the two that are about the grid itself: the order the phrases are in, and — in edit mode — arranging them by hand. The two mode toggles that used to head it are in the topbar now, beside Rest. **Only the first n cells are rendered** — see `core/virtual.ts`

**Three sizes of jump**, on the rail and on the category bar alike: a nudge (one chevron), a page (two chevrons), and an end (a chevron against a bar). The first two repeat while held, at `settings.repeatDelayMs`. They are ordered outward by how far they travel, so the three are told apart by position as well as by glyph. Two things are deliberate:

- **A page is the visible extent less one nudge's worth**, not the whole extent. Grid rows are not a uniform height and category tabs are pills of every width, so a jump of exactly one screen leaves something cut across the fold — a phrase half off the top, or half a category at the edge that a gaze user hits meaning its neighbour. The floor keeps a viewport smaller than the overlap from paging by nothing.
- **The grid rail drops its two page controls on a short screen** — `@media (max-height: 700px)`, keyed on `.scroll-btn-page`. Six controls stacked in a column need vertical room a short screen has better use for, and nothing becomes unreachable: a nudge repeats while it is held, so it crosses the same distance, and the ends still reach either end in one dwell. **No orientation clause here**, unlike the rule below: a landscape tablet is 768px tall and a landscape phone is 430px, so the height already tells them apart.
- **The two ends are hidden on a phone held upright** — `@media (max-width: 700px) and (orientation: portrait)`, keyed on `.filter-arrow-end`. Six arrows and the tools leave a portrait phone almost no room for the tabs they exist to reach, and paging reaches either end too, only a screen at a time. **Width alone is not the test**: a tablet in portrait is over 700px and keeps all six.

The arrow dividers are keyed off **which side of the scroller** an arrow is on (`.filter-scroll ~ .filter-arrow`), not off its position in the row. They were `:last-child` and `:nth-last-child(2)`, written when there were two arrows on the right; there are three now, and two on a portrait phone, so counting from the end kept being wrong.
- `talk/phrase-text.tsx` - `PhraseText`, which draws a phrase's slots and any markdown in it. Used by the grid cell and the emergency bar, so a phrase looks the same wherever it is shown
- `talk/topbar.tsx`, `talk/filter-bar.tsx`, `talk/emergency.tsx`, `talk/slots.tsx`, `talk/editors.tsx` - One surface each. **`editors.tsx` holds no phrase editor** — it is the strip on the message box's lower border (`PhraseEditBar`, rendered by the topbar so it can be positioned against it), the grid a category is chosen from, and `CategoryModal`, which is about a category rather than a phrase. The topbar carries **all three modes in one strip** — edit, Rest, auto-speak, in that order, centred on the top border of the message box and overlapping it, since they are the same kind of thing and the middle of the screen's top is where a gaze on its way anywhere passes. Riding on the border rather than sitting in a band above it is what keeps the cost to the grid at 2px instead of 18px; what it costs instead is that the top-centre of the message box answers to a mode rather than to the caret. It stands on **an opaque ground**, because it sits on the box and the border and the typed text used to show through the gaps between the three — `--border-ground`, which every control on either box's border shares. `topbar` padding-top and `.topbar-modes` `top` have to stay equal, and at least half the strip's height — the toggles plus its own padding, 16px today — or the strip drifts off the border or over the top of the bar. **The strip never sits left of the message box.** It is centred on the bar, where Rest is looked for without looking, and on a bar holding one box that centre is on the box; with the question beside the answer on a wide screen it is over the gap between them. So `left` is `max()` of the bar's centre and the place that puts the strip's left edge on the box's, and `topbar.tsx` measures `--box-left` and `--modes-half` for the second. **Pushed only as far as it has to go, not re-centred on the box** — re-centring would move Rest a long way every time listen mode opened, and a control that jumps when a different one is used has to be found again. Unmeasured, both are nought and it is the bar's centre, as it always was. **Nothing acts on the message from outside the box.** The three that do ride the **right end of the upper border** as `.topbar-actions`, where the language and the voice used to sit; those have gone to the **right end of the lower** one, being neither about the message nor urgent, set once and left. **Paste keeps the middle and the primary keeps the end** — speak outside edit mode, save inside it, `.is-primary`, told apart by the accent and by being last rather than by size. It was a 3rem glyph for a while; **every control on either box's border is the microphone's size now** — a 1.5rem control with a 1.2rem glyph, in a quarter-rem of ground — so the border furniture reads as one set rather than as things added one at a time. `.topbar` padding is half a strip's height, a rem, and `.topbar-modes` `top` equals it. What is left in the rail beside the box is the menu and the keyboard, which are about the app rather than about the message, and the board gets the whole of the rest. `.topbar-actions` packs its three **1.25rem apart rather than the mode strip's 0.75rem**: that much clears the invisible area each carries, so no two overlap anywhere — the modes can afford to be tighter, being three states of one thing where picking the wrong one costs a dwell, while one of these deletes a phrase. Both strips hang off `.message-wrap`, not the pair of boxes: they act on the message, and with listen mode open on a wide screen the pair's corners belong to the question. So each border holds one kind of thing — a mode in the middle of the upper one, the microphone at its left, the actions at its right; the slot that empties the box at the left of the lower one, the two values at its right, and the edit strip in its middle. **The left end of the lower border carries the slot that empties the box** — Clear, or Undo, and in edit mode *start a new phrase* — moved off the rail for the width, which is the same bargain the modes struck above. It is `.icon-btn.on-border`: painted at a mode toggle's size, with a mode toggle's invisible hit area. **The lower border because the upper one is full** — a mode in the middle, the values at the right, the microphone at the left — and because two controls on one side of a box 3.5rem tall cannot keep the air this app puts between gaze targets, while one at each end can, the distance only growing as the box does. Down there it shares the line with `.edit-bar`, which is centred, and it sits a layer above it: on a screen too narrow for that strip's content the two meet, and this is the smaller, fixed target while the strip scrolls sideways to reach the rest of itself. **It hangs off `.message-wrap`, not off `.text-display-wrap`** — the wrapper's left edge is the *question's* on a wide screen with listen mode open, and a Clear riding that border would be a Clear on somebody else's words. The microphone and the two value controls stay on the wrapper for the opposite reason: it is the same size in the same place either way, so they hold one point on screen. **Every control that rides a border stands on the one ground**, `--border-ground` — the microphone, the modes, the actions, this one, the heard box's tools, the language and the voice, and the edit strip. **Grey at fifteen per cent, mixed into the bar rather than laid over it.** A translucent ground was tried and let the box's border run straight through the glyphs — the focused box's green line crossing copy, paste and speak — which is what these grounds exist to stop; solid black was the first answer to that, and this is the same answer in a lighter grey. `tests/app/App.test.tsx` holds every strip to the token and every glyph to the microphone's size. `.topbar` padding is equal top and bottom now, half a strip's height either way. **The box has a strip on each border in edit mode** — the modes above, the category and the voice below — and the lower one is sized by the same rule as the upper, out of a single `--edit-bar-inset` that is both the bar's padding-bottom in edit mode and the strip's own `bottom`. It exists because the defaults are not this codebase's style — no semicolons, single quotes, no parentheses round a sole arrow parameter — and a formatter run without it rewrites every statement in the tree. **It also names what oxfmt must not touch**: oxfmt formats JSON, CSS, HTML and YAML as well as TypeScript, so left alone it reflows the 44,000-line phrase table, the stylesheet whose order is load-bearing, the pointer probe, and the lockfile. `package.json`'s `format` script names the four code directories for the same reason, so the two would have to fail together
- `tools/pointer-probe.html` - **The pointer probe**, opened with `pnpm probe`. Standalone HTML, no build step, deliberately **not** in `public/` — everything there ships to production and is indexed. It does two jobs: it says what a browser will and will not tell a page about the pointer (run the trip, read the log), and it measures the stream so `STALL_MS` can be tuned against real hardware rather than estimated. It restates the constants from `ui/dwell.ts` to do the second, and `tests/app/structure.test.ts` fails if the two ever disagree — an instrument quietly at odds with the code it is tuning is worse than none. The **block the main thread** buttons are there for the one thing that could make a present pointer look absent; Peri's longest single task is the rail's jump-to-bottom, which renders the whole table at once for roughly 50ms
- `tools/mic-probe.html` - **The microphone probe**, opened with `pnpm mic-probe`. Standalone HTML, no build step, and deliberately **not** in `public/` for the reason the pointer probe is not. It answers one question: *which microphone is the speech recogniser actually listening to.* `SpeechRecognition` is documented to take neither a device nor a stream nor a gain, which would mean listen mode cannot be given a device setting at all and a picker would move a control that steers nothing — so the claim is measured rather than believed. It opens **every** input at once with a live level meter, names which one the browser calls the default, and logs each transcript beside whichever device was loudest when it arrived; make one device hot and the rest cold, and the pairing says which one the recogniser was on. It also dumps every property a `SpeechRecognition` exposes, since a device option would have to be among them. `tests/app/structure.test.ts` holds it to reaching for the same recogniser `listen/recognition.ts` does — an instrument measuring a different object from the one the app uses answers a question nobody asked
- `tools/release.ts` - **The version commit**, `pnpm release`: the pull request's label, `package.json` bumped by it, committed on the branch as the last thing before it merges — see *Versioning*
- `tools/publish.ts` - **Puts a release in front of people**: finds Netlify's build of the release commit, publishes that one, and then asks the site what it is serving. Run by the Publish workflow, which is the only thing holding the Netlify token
- `tools/translate-table.ts` - Translates the shipped phrase table into a file the app carries, run once per language with `pnpm translate <lang>` and a `GOOGLE_TRANSLATE_KEY` — **an unrestricted key, and not the app's**, since the referrer restriction that makes the app's safe to inline is one Node cannot satisfy. **A build step and not a runtime one** because the emergency bar must never wait on a network. It **merges** rather than replaces, so the hand-written emergency phrases are not quietly taken over by a machine, and the output is meant to be read before it is committed — these are phrases somebody will say to a nurse about their own body, and a plausible mistranslation is worse than an English sentence a listener has to work at
- `pnpm-workspace.yaml` - **pnpm's settings, and not a workspace.** pnpm 11 stopped reading the `pnpm` field in `package.json`, so this is where they live. It answers one question: whether esbuild may run its install script. Until something answers it pnpm refuses *every* command with `ERR_PNPM_IGNORED_BUILDS` — `pnpm check` and the Netlify build included — so an unanswered prompt is a broken deploy. The answer is yes, because it is not a new trust decision: esbuild is how Vite builds this app and runs on every build regardless. **It has to be committed**, or pnpm writes the placeholder again on the next machine
- `.mise.toml` - Toolchain versions for Node.js and pnpm

The site is **indexed**: `public/robots.txt` allows everything and `index.html` carries no `robots` meta tag. The two are a pair — if either ever says no, the other has to as well, or the site ends up half-hidden. `tests/app/shell.test.ts` fails if they disagree.

## Testing

Run `pnpm check` before handing work back — it runs `format:check`, `typecheck`, `lint`, and `test` in sequence. `pnpm test:watch` while iterating. **GitHub Actions runs the same command** on every pull request and on main, and main will not take a change until it passes — see *Checks, releases and publishing*. Running it here first is still the point: a red check five minutes after a push is five minutes lost.

**A test's timeout is for one that has hung, not one that is slow.** It is 30 seconds here rather than Vitest's five: a whole-app test that loads the board a few times is seconds of work, and under the suite in parallel on a CI runner several of them passed five seconds. A red run over work that was fine is worse than a hung test taking half a minute to say so.

**The format check is first because it is the cheapest.** It answers in about 20ms and names the file, so an unformatted tree fails in under a second rather than after three minutes of tests. `pnpm format` fixes whatever it reports. It takes its paths from the `format` script rather than restating them — `pnpm format --check` — so the two cannot drift apart about which directories are formatted.

**Every test lives under `tests/`, mirroring the tree it covers** — `tests/core/`, `tests/ui/`, `tests/sync/`, `tests/functions/`, and `tests/app/` for the ones that drive the whole app through `App`. `tests/setup.ts` is the shared setup file.

They used to sit beside the code, which is the nicer arrangement and cost a deploy: **`netlify/functions/` publishes every file in it as a function**, so `sync.test.ts` was deployed as one and took the build down with it. A rule with one exception is a rule somebody forgets, so there is no exception — `tests/app/structure.test.ts` fails if a `.test.ts` appears under `src/` or `netlify/`.

Two things worth knowing when adding to them:

- The app grid renders every phrase in the table, so query it with `container.querySelector` rather than Testing Library's `getByRole` — building an accessibility tree over a couple of thousand cells for each lookup is slow enough to matter.
- **The grid is given a viewport by `tests/setup.ts`**, and windows as it does in a browser. jsdom lays nothing out, so without one the grid falls back to rendering every cell — two and a half thousand of them for each test that opened the board, which was most of what this suite spent its time on. The stubs are keyed on the grid's own classes, because what jsdom reports about everything else is load-bearing: the message box grows by what it can measure and has to find nothing. **`unmeasuredGrid()` puts the absence back**, for the tests about that fallback and for the few that need the whole board on screen to find one phrase among thousands.
- **`performance.now()` is faked by `vi.useFakeTimers()`.** A benchmark that reads it measures the fake clock and reports whatever `advanceTimersByTime` was given. Capture the real one at module load.
- Dwell is timer-driven. Use `vi.useFakeTimers()` and advance inside `act()`; the app also uses a zero-delay timer to place the cursor after inserting a phrase, so advance the clock after any interaction before asserting.

When fixing a bug, add the test that fails without the fix, then confirm it actually fails when the fix is reverted. Several tests here are explicit regression guards and say so in a comment.

## Styling

This project uses **Tailwind CSS v4** through the `@tailwindcss/vite` plugin configured in `vite.config.ts`. `src/index.css` imports Tailwind with `@import 'tailwindcss';`. Use Tailwind utility classes directly in JSX and put global CSS or Tailwind v4 theme customization in `src/index.css`. This scaffold does not need a Tailwind config file or PostCSS config.

`src/main.tsx` imports `src/index.css`, so global font wiring belongs in `src/index.css`. Keep CSS `@import` statements first, then add any `@font-face` rules and font-family defaults there.

**Tailwind is given an allowlist, not the whole project.** `src/index.css` opens with `@import 'tailwindcss' source(none)` and then names `./**/*.tsx` minus tests. Left to scan everything, it takes any word that looks like a utility name — `container.querySelector` written in this file shipped a real `.container` rule with five media queries to every user, and words in the stylesheet's own property values added ten more. Narrowing it took three kilobytes off the bundle. Add to the `@source` list if a class ever needs to come from somewhere else.

**The muted grey is held to 7:1.** `--text-muted` carries every sublabel, hint and count in the app, and it was `#888` — 4.7:1 on a cell and **4.3:1 on one being hovered**, under what AA asks for, in the one state a control is in while it is being read. It is `#b0b0b0` now, which clears AAA against every surface in the palette. `tests/app/structure.test.ts` does the arithmetic rather than trusting an eye.

**The message box grows with what is in it**, from one line to five or a third of a short screen, whichever is less. `topbar.tsx` measures — a line is however many characters fit at this text size and this width, which is not a number the app can know — and `max-height` in the stylesheet is what clamps it, so the box cannot eat the board. The height is cleared before each measurement or the box only ever grows, `scrollHeight` including whatever room it already has. **The border is added back on**: the height is `border-box` and `scrollHeight` leaves the border out, so a box set to exactly what its text measured was two pixels short — the scroll arrows appeared on every box past one line, and the room they take rewrapped the text into one that really did overflow. It was fixed at one line with the overflow scrolled and the scrollbar hidden, which put a long message above the fold with no way back to it. **Past the cap it scrolls, by dwell**: `BoxScroll` puts an up and a down inside the box's right edge while there is more than shows, in padding the box gives up only then (`.has-scroll`) so no word sits under one. A textarea holds no children, so the controls a pane hangs above and below its content had nowhere to go — inside the edge is the one place left, inset from the top and bottom by more than the strips on the border reach into the box. **Where nothing can be measured, nothing is set** — jsdom reports nought, and a box set to nought is a box nobody can see.

**Text is sized in `rem`, never in pixels.** The scale runs 0.8rem to 2.5rem with **1rem as normal**, which is the browser's own default rather than a number this app picked. The geometry that *bounds* text is in `rem` too — the message box and the icon buttons beside it, the edit strip and its inset, the grid cell's minimum height, the topbar padding that anchors the mode strip — because a box fixed in pixels around text that scales is a box that clips the moment somebody turns the zoom up. Spacing that holds nothing is left in pixels.

**The stylesheet is one file on purpose.** It is ordered by accretion rather than by concern — the rules for reordering categories sit two thousand lines below the rules for the tabs they reorder — so splitting it into partials would mean either importing the same concern twice or moving blocks past each other. Moving them changes the cascade wherever two selectors have equal specificity, and jsdom lays nothing out, so no test here would catch the difference. Reorganise it only alongside a visual comparison against a deploy preview.

## Phrases and slots

Phrases in `phrasetable.json` can carry fill-in-the-blank slots — `Please turn {control} the lights`. A slot's options come from one of three places, resolved in `resolveSlot`:

1. An inline quoted list in the placeholder itself (`{['music', 'tv']}`), which always wins.
2. The user's own list of the same name, edited under **Menu → Aliases** and stored separately from the phrase store. This is where `{contact}` and `{name...}` come from — the table ships those two empty, because there is nowhere in the data to put a particular person.
3. The table's own `aliases` block, for `{pronouns}`, `{direction}`, `{bodyparts}` and friends — the seed for the lists above.

**Every list is the user's to change.** `core/store.ts` keeps an `AliasStore` — `lists`, a record of the list name as a phrase writes it against its words, and `hidden`, the shipped names they took away — and **only what they touched is in it**: a key that is absent from both follows the table into the next release. A key that is present wins outright, **an empty list included**, because emptying one is a thing somebody can mean and falling back to the shipped words would make it the one edit the panel could not carry out. A list they invent is reached by writing its name in a phrase, and is the only kind that can be deleted rather than merely emptied.

**Two controls sit above the lists**, because they are about the lists rather than about any one list's words: a **+** that adds one, and an **edit toggle** that turns every heading into a name field with a delete beside it. The `+` cannot ask for a name — it is one dwell, and naming is a keyboard job — so it makes `new-list`, opens it, and switches the naming mode on so the field is there to type in. A name is committed on Enter or on leaving the field, never per keystroke: a rename is a change of key, and rewriting it letter by letter would leave lists called "d", "dr", "dri", taking the focus with them.

**Every list can be renamed and deleted, the table's included.** That means a shipped list has to be removable, and leaving it out of `lists` cannot do it — the table would put it straight back — so the store has a **`hidden`** set beside the lists, for the same reason `PhraseStore.hidden` exists. `aliasOverlay` turns a hidden name into an **empty** list rather than a missing one: present-but-empty is what stops the lookup falling through to the table, which is the whole of what deleting one has to mean. Renaming a shipped list is built out of the same thing — the words move to the new name and the old one is hidden — and yes, the phrases that said `{pronouns}` then resolve to nothing. That is the user's call to make about their own board.

**A merge never applies `hidden`.** Hiding a list is a removal, and only *replace* applies removals — the same rule phrases follow, for the same reason: a file somebody else made must not take a list off your device.

**The panel folds, and each list arranges.** One list open at a time, **all of them closed on arrival**, and opening one scrolls it to the top of the pane — `bodyparts` alone is fifty words to scroll past to reach the list you came for. The guide's headings fold on the same terms but open their first section on arrival, and the difference is deliberate: a guide is opened to read something, and this is opened to reach one list out of ten. A closed list is **unmounted, not hidden**, or a screen reader reads out three hundred words nobody asked for. The open one draws its words as a **grid**, and carries the two arrangements the category tabs offer — A–Z, or the order the words were put in — plus an arrange mode and a word-editing mode. Seven things about it:

- **A–Z is a view.** The order underneath is left alone, so going to A–Z and back is not a way to lose an arrangement. It is kept under `peri_alias_sort`, its own small key: the *order* is content and travels in a backup as the order of each list, but which of the two is being looked at does not.
- **Arranging out of A–Z captures what was on screen.** The move is applied to the shown order and becomes the user's own, exactly as `reorderCategories` does — a move applied to the hidden order would land somewhere they could not see. Every route to the sort mode goes through one setter, so that switch is remembered too.
- **The panel bounds its own height** — `.alias-panel`, in `dvh`, rather than the `.settings-panel` it borrowed at first. That one fills whatever it is given, which for Settings is the viewport; this panel hangs from the menu and is given the height of its own lists, and a pane told to fill that can never overflow. The symptom is not a pane that scrolls badly but one that does not scroll at all: no arrows, and everything past the bottom of the screen out of reach, there being no wheel and no scrollbar here.
- **A chip is one of three things and never two.** Plain, which is most of the time: text to read and no target at all. **Being edited**: a field to reword it and an × to take it off. **Being arranged**: something to pick up and put down. Two targets in one place is the worst thing to give somebody aiming by gaze — a dwell meant to put a word down would delete it. **Deleting is offered only while editing**, because the × used to sit on every chip in every state, which is a delete under the pointer of somebody reading their own words. Each mode turns the other off and puts down whatever was in the air; closing the list puts both away.
- **A word keeps the case it is typed in; a list's name does not.** A name is the key a slot looks up, so it folds to lower case. A word is what comes out of the speaker, so "Mum" stays "Mum". One `NameField` serves both and takes the difference as a `normalise` prop.
- **A deleted list can be put back too**, from the undo beside the `+` and the pencil. Deleting a list is the largest loss the panel hands out — fifty words in one dwell, and every phrase that named it left with a blank. What goes back is **the state the name was in, not the words that were on show**: for a list the table ships and nobody had touched, that means un-hiding it and storing nothing, because writing the table's own words into the store would pin the list to this release and stop it following the table into the next one.
- **The last deletions can be put back.** Deleting is the one edit here with nothing to show for it afterwards — a word that is gone leaves no chip to fix — so every removal is kept with **the index it had in the stored order**, and undo splices it back there. The stored order, not the shown one: an undo out of A–Z must repair the list rather than rearrange it. The stack is per list, lives as long as the panel is open, and is never written down — an undo somebody comes back tomorrow for is a backup, and there is one of those under the next menu item. The control goes **quiet rather than away** with nothing to put back, and names the word it would restore.

**Two older shapes are still read.** This panel was **My details** and wrote a `{ name, contacts }` object under `dwellspeak_profile`; those were always these same lists behind the scenes, so `loadAliases` folds one in the first time it finds no alias store. And the store was a bare record of lists before anything could be deleted, so `readAliases` takes either that or `{ lists, hidden }` — which is also what a backup written in between carries. Renaming a menu item must not lose somebody their contacts.

How many options a slot ends up with decides the interaction, so mind the boundaries: **none** is a blank the caret lands in for typing, **exactly one** is substituted straight into the text with no picker, and **two or more** opens the slot picker. `hasChoices` and `choosableSlots` both key off `options.length > 1` for that reason.

**`BLANK` is the empty string.** A blank puts no characters into what gets said, copied or typed over — the gap is the placeholder. Two things carry it, and both are needed, because a blank nobody can see is a blank nobody fills:

- On the board, `.phrase-slot.is-blank` keeps a `min-width`, so the dashed underline is still drawn across an empty gap.
- In the message box, `composeWithBlank` reports where the gap landed and the caret is put there. It has to *report* it, because there is nothing left in the text to search for — and `indexOf('')` answers with the position you asked about, which would land the caret at the start of every phrase inserted, blank or not.

Two consequences worth knowing:

- **Ask `hasBlank(segments)`, never `text.includes(BLANK)`.** The second is true of every phrase on the board. It emptied three tests silently when `BLANK` changed, rather than failing them.
- **`composeWithBlank` tracks the gap with a private-use character, not with `BLANK`.** Composing collapses spaces and trims ends, which moves every offset after the point it changes, so the only way to know where a blank *ended up* is to leave something there while that happens. It is not whitespace, so a blank spaces exactly as the old `___` did — and a word typed into the gap needs no spacing of its own, including before punctuation.

Slot options are baked in at parse time, so `buildPhrases(aliases)` re-parses the table when a list changes. Phrase ids hash the *source* text rather than the rendered text, so saved edits survive an alias change.

**A phrase carries both what it reads as and what it was written as.** `text` is the display form, with every slot resolved into a label; `source` is the raw `I want the {['red', 'blue']} one`. The second cannot be rebuilt from the first — "red/blue" is a label, and `{pronouns}` has become a list of words that would no longer follow the alias table or the user's own details.

Which one to use is not a matter of taste:

- **The editor loads `source`.** It loaded `text` for most of this app's life, so opening a fill-in-the-blank phrase showed "I want the red/blue one" and saving stored exactly that — flattening the slot for good, silently, on a phrase somebody had only opened to look at. `tests/app/App.test.tsx` guards both halves: what the box shows, and that a phrase opened and saved unchanged still offers its choices.
- **Anything that speaks, fetches or previews composes first.** The draft holds `source`, so the voice preview and `warmVoice` both run it through `compose(parseSegments(…))`. Sent raw, ElevenLabs reads the brackets aloud and stores the clip under text nothing ever asks for again — and the phrase drops back to the device voice, having been paid for twice.
- **Everything else — speech, search, the grid, a phrase's accessible label — uses `text`.**

## Editing a phrase

**In edit mode the two controls at the box's lower-right corner are the phrase's, not the board's** — the voice it is said in, and the language that voice is for. `PhraseEditBar` carries no voice picker of its own for that reason: one pair of controls meaning whichever of the two the mode says, rather than two pairs that look alike and are not. The language is still the board's, because a phrase's voice is remembered *per* language and that is the one the lookup will use. **The pair is drawn in edit mode at any width**, unlike outside it, where it is gated on `WIDE_ENOUGH` to avoid building the device's voice list on a phone that never shows it: this is the only place a phrase can be given a voice now, and a control that exists on a monitor and not on a phone is a feature somebody cannot reach.

**In edit mode the message box is the phrase editor.** There was a dialog for it, and a dialog is the wrong shape for a board driven by gaze: it covered the very phrases being edited, it had to be got out of before anything else could be reached, and every one of its controls was a target somewhere the pointer had never been. So there is always a draft — `talk/use-editor.ts` — and choosing a phrase points the draft at it rather than opening anything.

- **The rail changes with the mode, in the same three places.** Speak, copy and paste become save, delete and paste; Clear becomes "start a new phrase". Paste is the one that means the same thing either way, which is why it keeps the end of the row while the two beside it change. Delete **goes quiet rather than away** while there is nothing to delete, for the reason the emergency bar's add control does: a control that comes and goes moves the ones beside it, and these are aimed at rather than read.
- **A second strip rides the box's lower border**, centred on it exactly as the modes ride the upper one, and carrying the two things a phrase has besides its words — the category and the voice. Both are triggers onto a full-screen grid, because that is the only shape of "one out of many" a dwell can work. The category was a native `<select>`, whose list the operating system draws outside the page, where nothing can be hovered at all. Its grid ends in a tile that is not a category: **New category…** hands over to the same `CategoryModal` the tabs use, since naming one is a keyboard job. **The two are one number**, `--edit-bar-inset`: it is `.topbar` padding-bottom in edit mode, which is where the box's lower border falls, and it is the strip's own `bottom`, which with `translateY(50%)` is where the strip's centre line falls. It is half the strip's stated height, so the lower edge reaches the bottom of the bar and no further. Written as two numbers they drifted apart at the first change — the padding grew and the strip stayed put, leaving it centred 20px *below* the border it rides.
- **The same wording cannot be filed twice in one category.** A second copy is a cell somebody has to read past to reach the one they meant, so Save goes quiet and the strip says *Already on the board* — a control that has gone quiet explains nothing by itself. Matched on the source, folded to lower case with its spaces collapsed, and **only within a category**: the table lists "Good morning" under Interpersonal, Texting and Time of Day on purpose, because somebody looks in whichever of the three they think in. `duplicateOf` in `use-board.ts` keys the board once and answers in constant time; a phrase does not duplicate itself, or opening one to fix a typo could never be saved.
- **Saving closes nothing, because nothing was opened.** The draft goes back to blank and a toast says what happened — without it a save has no visible result beyond one cell appearing somewhere among a couple of thousand.
- **A new phrase takes the board to where it was filed.** Anywhere but the tab in front of them it lands among a couple of thousand cells, and all somebody has to show for writing one is a toast that fades. Three cases do not move, and none is an exception to that: on **All** the phrase is already on screen, the **emergency bar** is on screen under every tab, and a phrase being **reworded** is one somebody is moving *out* of where they are — refiling several out of one category is a run they would be thrown out of after the first. **Keeping a message is the case with the least to show for it otherwise**, the record it came off being left exactly as it was. The move holds the dwells (`holdDwellsUntilMoved`) because every cell has just been replaced under a pointer that has not moved and in edit mode the one landing underneath opens for rewording; a save that leaves somebody where they were holds nothing, having replaced nothing. Note that **a tab cannot be changed in edit mode** — there a category tab opens for renaming — so the tab a save happens on is the one edit mode was entered on, or one of the four pinned ones.
- **And it shows them where it went**, in three parts, because a save that leaves nothing on screen but a toast is a save with nothing to show for it. The new cell takes **the mark the last phrase chosen takes** — one mark meaning *that one, and it went there*, rather than a second one to learn, and it goes the same way, on the next dwell whatever that is. The grid **brings the cell into view**, centred, a cell against the top edge sitting under the message box and one against the bottom under the emergency bar. And the bar **brings the tab to its middle**, but only where the board moved by itself (`FilterBar.centreOn`): forty-two categories is several screens of tabs, while a tab somebody dwelled on is one they were already looking at, and sliding that out from under a gaze that has not moved is how the next dwell lands on its neighbour. `landed` in `talk.tsx` carries both halves. Two things make the scroll work rather than quietly do nothing: the cell carries `data-phrase`, since the list is rearranged under it by four orders, and **the render window is grown to reach it** — it starts again at a screenful on arriving at a tab and a category runs to a hundred and eighty phrases, so the new cell is often past the end of what is rendered, and a cell that does not exist is nothing to scroll to. Both are adjusted during the render that names the phrase, which is why the scroll can ask once rather than watch the window.
- **Entering edit mode on a category files the next new phrase under it.** Somebody who switches to Greetings and then reaches for edit mode is adding to Greetings, nearly every time, and what they got instead was a picker landing on wherever the last phrase went — which after one trip to another tab is the wrong answer for every phrase after it, each costing a dwell on the trigger, a dwell on a tile and a dwell on Done to put right. It is the same `peri_recent` a save writes, through `fileUnder` in `talk.tsx`, so there is one answer to *where does a new phrase go* rather than two. **Only where the tab is a category**: All is every category at once and Sent, Answers and Translations are records of what was said, so none of the four is somewhere a phrase can be filed and each leaves the last choice standing rather than throwing it away and making somebody pick again. `allCategories.includes` is the whole of that test, those four being the only tabs that are not in it. **Only on the way in**, too — a draft that refiled itself whenever somebody glanced at another tab would move a phrase they had already chosen a category for.
- **The message and the draft are separate.** Entering edit mode carries the message in as a new phrase, so "keep what I just wrote" is a mode switch rather than a feature — but writing a phrase never writes the message, and leaving edit mode gives it back untouched.
- **The grid does not narrow to the draft.** `currentWord` filters the board while a message is being composed; in edit mode `filterWord` is empty, or the phrases somebody came to edit would disappear as they typed. That holds however the letters arrive — including from Peri's own keyboard, where narrowing is most of the point. `tests/app/App.test.tsx` drives all three modes through the keys. The guard only bites when edit mode was entered with something already composed, which is the only way to test it: writing a phrase writes the draft and never the message, so a test that clears the box first passes with the guard taken out.
- **Edit mode is drawn on the box's own border**, dashed and accent-tinted, rather than as an outline over it. A textarea already has a border and an outline sits just outside one, so the two read as a double line around a single box; the focus colour is restated at the same specificity so it still shows through.
- **The board opens talking, and with the caret in the box.** Auto-speak is the state every load starts in, and the message box carries `autoFocus` so somebody with a keyboard can type the first thing they want to say without having to place the caret first — the one thing a dwell could not do at all until `useCaretDwell`. A programmatic focus does not raise a phone's on-screen keyboard, which needs a real gesture.
- **Three states, two controls, and each control means its own state.** A dwell on a phrase either says it (**auto-speak**), collects it (**composing**), or opens it (**edit**), and never more than one of those. Auto-speak is where the board ships, so opening Peri for the first time is enough to say something. **Switching one on switches the other off; switching one off leaves the other alone** — speaking and rewording ask opposite things of the same dwell, so the board cannot be in both, but *not speaking* is not a request to start rewording. They sat in a ring instead, where auto-speak off landed in edit mode: the one toggle somebody building a sentence reaches for put them in the one mode where a dwell changes the board, and composing, which is what they were after, was two dwells away — the furthest apart pair in the ring was the pair used most. Every state is one dwell from the other two now, and neither control ever does nothing. `setMode` in `talk.tsx` is the only thing that writes any of it, and **the microphone writes it too** — see *Listen mode*.

`Draft` derives everything it can rather than copying it: `text`, `category` and `voice` are stored only once touched, and everything else is read off the phrase each render, so a draft cannot go stale against a store that changed underneath it.

## Placing the caret

A text box is the one control dwell alone could not drive. Hovering can focus it, but the caret only ever moved when something was clicked — and a click is the input a gaze user does not have. Typing itself comes from whatever keyboard they already use; saying *where* to type is the part no keyboard supplies. So **the message box answers to a dwell of its own**, which puts the caret under the pointer: `useCaretDwell` in `ui/caret.ts`. There were two boxes until the phrase editor moved onto the main screen; there is one now, doing both jobs, and the dwell is on it in both of them.

- **On the message box the caret does a second job.** It decides which word the grid narrows itself to, so placing it is how a gaze user says which word to finish. That state is tracked rather than read off the box, so the hook reports where it put the caret and `use-composer`'s `setCursor` is told. jsdom happens to reach the same state by a second route — `setSelectionRange` fires a `selectionchange` that React turns into `onSelect`, already wired to the same setter — so **no app test can isolate that wiring**, and `ui/caret.test.tsx` holds it instead. It is worth holding: `selectionchange` on a form control is a late addition, and where it is missing the grid quietly completes a word the caret has left.
- **In edit mode the box holds a phrase, and is still a box.** It was `readOnly` there — a button whose hold opened the editor dialog — with the caret dwell switched off and a second dwell in its place. There is no dialog to open, so the second dwell is gone and the caret one runs in both modes. What does not run in edit mode is `onPlace`: the caret it reports belongs to the composer, and it decides which word the grid narrows itself to.
- **The message box used to stop arming once it held focus.** That gate was protecting something real, a pointer parked on the box while its owner types, but it also made the caret placeable exactly once, on the way in. Aiming settles it instead: a pointer that has not moved does not re-arm, focus or no focus.
- **Two APIs answer the question and they are not equally trustworthy.** `caretPositionFromPoint` answers about a form control *as* a form control — the field itself and a character index into its value — and is taken whatever the value looks like. `caretRangeFromPoint` reaches inside and answers about the run of text it found there, which is the whole value only while the value is one line; on a phrase written over several it would land the caret nowhere near the pointer, so it is **declined rather than guessed at**. Null means leave the caret alone; putting it at nought would jump to the front of the phrase on every dwell.
- **Where neither exists the box is still focused.** That is the difference between a box that can be typed into and one that cannot.
- **Aiming somewhere new re-arms the dwell.** It fires once on arrival, so without that the caret could be placed only by leaving the box and coming back — but gaze never holds perfectly still, so `AIM_TOLERANCE` has to sit above the jitter.
- **The distance is measured from where the wait began, which is why the hook keeps two positions.** `aim` is where the pointer is, and is what the caret is placed by; `armedAt` is where the current wait started, and is what `movedAway` is asked about. Measuring each movement against the one before it looks equivalent and is not: a pointer does not jump, it crosses a phrase in three-pixel steps, and nothing ever exceeds the tolerance. That shipped, and the symptom was the feature simply not working — leaving the box and coming back was still the only way to place the caret twice.
- **The box restarts its own fill.** Every other control remounts its `dwell-bar` to replay the animation, but a textarea can hold no children, so the fill is a CSS animation on the box itself and the `dwelling` class does not change across a re-arm — cancel and start land in one render, React writes nothing, and the bar keeps promising a firing that is no longer coming. `restartFill` takes the animation off, reads a layout property, and puts it back. jsdom lays nothing out, so nothing tests it.
- **Testing any of this needs a `pointermove` without a `pointerenter`**: a pointer travelling within an element only fires the first, and firing the second re-arms the dwell by itself and makes the test pass with the re-arming taken out. It also needs **more than one move** — a single sixty-pixel jump passes whichever position the distance is measured from.
- **Keeping still is how a gaze selects.** A dwell can say one thing — *here* — and a selection is two, so the second is said by not moving: rest once and the caret lands under the pointer, keep resting and `wordAt` picks out the word around it, keep resting again and the whole value goes. Each step replays the fill, and the fill **stops** at the end of the hold rather than promising a firing that would do nothing — which is also the only way a test can see where a hold ended, since a second select-all looks exactly like the first. A field holding one word finishes a step early for that reason. It is `selectOnHold`, and **the message box does not ask for it**: a pointer parked over the message while its owner reads the board is at rest without meaning anything by it, and the caret there also decides which word the grid completes. In the Aliases panel, where a field is opened in order to reword something, a rest is intent.
- **Every single-line field in the app is one of these**, through `DwellInput` in `ui/controls.tsx` — the Aliases panel's names, words and add rows, the ElevenLabs and Anthropic keys and the sync passphrase, a category's name, and the figures in a spinner. It was local to the Aliases panel, which left the three account rows in Settings taking the caret only on a click: Peri's own keyboard types into whatever field has the caret, so setting any of them up by gaze was impossible. **The spinner's figures are `type="text"` with `inputMode="numeric"`**, because a number field refuses `setSelectionRange` and the first dwell to fire on one would have thrown. A box you cannot put the caret into is a box you can only clear and retype, which is the whole of what a keyboard cannot supply. The fill is painted as a background layer (`.caret-field.dwelling`) for the reason the message box paints its own that way: an input can hold no children, so there is nowhere to put a `.dwell-bar`.
- **Only the pointer handlers go on the textarea**, which is why the hook hands back nothing else. Spreading the whole set from `useDwellControl` would put its Enter/Space handling on a box people type into, and the first space typed would be swallowed.

## Markdown in a phrase

A phrase may carry markdown: `**bold**`, `*italic*`, `~~struck~~`, `` `code` ``, `# headings` and `- bullets`. It is a way of making a button readable at a glance and nothing more. `core/markdown.ts` holds all of it.

**The rule everything else follows from: what the eye sees is styled, what the ear hears is the words.** `stripMarkdown` and `layout` walk the same parse, and `core/markdown.test.ts` asserts they agree on every case — if they ever come apart, a phrase becomes unfindable or gets spoken wrong.

- **Stripping happens once, inside `speak()`.** Every route to the synthesiser can arrive with asterisks in hand, because the message box keeps them. Doing it at the single place utterances are created is what makes "the app never says *asterisk asterisk*" a property rather than a habit. `warmVoice` and the warm-up in `useBoard` strip the same way **or the audio cache silently misses**: a clip stored under the marked-up text is one the phrase asking for it never finds, and on the emergency bar that reads as a phrase quietly losing the voice it was given.
- **The markup is kept in the message box and on the clipboard.** That is deliberate — the box is where a message is assembled and edited, and a copied message may be going somewhere that renders it. Speech and search are the things that strip.
- **Underscores emphasise between words, never inside one.** `_like this_` is italic and `snake_case_name` is a name — the rule every markdown supporting both delimiters settles on. Asterisks carry no such restriction, because nobody writes `snake*case*name` by accident. It is **two** guards, opening and closing, and a phrase with underscores only inside words exercises just the closing one: with nothing able to close, nothing opens either way. `snake_case here_ and` is what shows the opening guard doing anything.
- **Nothing is markup until it closes.** A lone `*` is a character somebody typed; "2 * 3" is arithmetic. A phrase must not lose characters while it is being written.
- **Markup never crosses a slot.** Slots are parsed out before any of this runs. The shipped table has slots and no markdown, and a phrase somebody writes has the reverse, so the two rarely meet — but the limit is real and tested rather than pretended away.
- **A heading is a style, not an `<h2>`, and a link is a style, not an `<a>`.** These sit inside a `role="button"`; real document structure there would be a lie to a screen reader, which reads the plain text off the button's own label. A real anchor would also give a gaze user two targets in one place, and the one they did not mean takes the board away mid-sentence.

### Links

`[label](url)`, added by **pasting or dropping a link** into the message box. A URL is the worst thing a board can hold as text — long, wrapping a whole row, and forty seconds of punctuation read aloud — so what goes on the button is its name.

- **The URL rides in `Style`; the label is the run's own text.** So everything that reads a phrase's words — speech, search, the button's label — gets the label and never the URL, without having to know links exist.
- **The label is the best thing on offer:** the text of a dragged link, then the page title a dragged tab carries (`text/x-moz-url`), then the site's own name with the `www.` off. It is flattened to one line, because a phrase reads newlines as new lines now, and it is deliberately *not* shortened — it sits in a box the user can edit, and quietly cutting somebody's words down is worse than showing all of them.
- **Only `http`, `https` and `mailto`.** Nothing renders a real anchor today, but this text is copied to a clipboard and pasted into things that will, and a board is a file people hand to each other. `javascript:` above all.
- **A phrase that is *nothing but* a link opens it in a new tab and speaks nothing.** `soleLink` draws that line, and where it falls is the whole safety argument: `[Today's menu](…)` is a button for going somewhere and reads as nothing said aloud, while "Have a look at [the menu](…) later" is a sentence somebody built — and a sentence must never lose its voice to a browser tab. Styling inside the label is still one link; a slot, a second line, or a word outside it is not. **Edit mode wins over it**, or a link would be a phrase nobody could ever reword.
- **A new tab, never this one.** The board is how somebody is talking; navigating it away mid-conversation takes their voice rather than lending them a browser. `noopener` so the page opened cannot reach back and drive the tab the board is in.
- **Opening can be refused, and it is said out loud when it is.** A browser only allows `window.open` off the back of a recent click, tap or key press — and a dwell is a timer firing after a pointer has rested, with no press anywhere in it. So the users this is for are the ones most likely to be blocked. `openLink` reports whether it managed, and the screen flashes a toast when it did not; silence would leave the choice looking simply broken.
- **A dwell user has no Ctrl-V**, so a control asks on their behalf, at the end of the topbar's rail — the one control there that means the same thing in both modes, which is why it keeps its place while the two beside it change. It gets the same treatment a keyboard paste does, address into `[label](url)` included, and lands at the caret. **It can be refused**: reading the clipboard needs permission and, in most browsers, a recent click or key press, and a dwell is a timer with no press in it — Firefox does not offer it to a page at all. So `pasteFromClipboard` answers `pasted | empty | refused` and the screen says which, exactly as it does behind a blocked link. Never disabled, because what is on the clipboard is not the app's to know until it asks.
- **A paste goes to the caret; a drop goes to the end.** A drop comes from outside the box and carries no caret of its own, and browsers disagree about where one would be — appending is at least the same answer every time. Telling the two apart in a test needs a caret that is *not* at the end, since typing leaves it there and both answers then look alike.
- **The parser has no escapes.** The first `]` closes the label and the first `)` closes the URL, so `linkMarkdown` strips brackets out of the label and percent-encodes a closing one in the URL. Only the closing bracket: an opening one ends nothing.
- **`tidy` and `compose` collapse spaces but not newlines.** They used to collapse every run of whitespace, which made a multi-line phrase impossible. Nothing in the shipped table has ever held a newline, so this narrowed what is collapsed rather than changing any phrase Peri comes with.

## Peri's own keyboard

**On iOS a gaze user cannot type at all without this.** The software keyboard is raised by a gesture and its keys are pressed by taps, and a pointer that only hovers has neither — `el.focus()` from a dwell is a timer firing, not a gesture, so it raises nothing, and a keyboard that did appear could not be operated. Every workaround dies on the same rock: `VirtualKeyboard.show()` is Chromium-only, dictation needs a tap to start, `inputmode` only chooses which keyboard *would* appear.

Typing was the one thing this app outsourced — `ui/caret.ts` still says "typing itself comes from whatever keyboard the user already has" — and that assumption held on macOS only because its Accessibility Keyboard happens to be dwell-operable. It is not a property of the platform, it was luck.

- **It types into whatever field has the caret**, rather than being wired into each box. That is what lets one keyboard serve the message box, the Aliases panel's names and words, a category name, the sync passphrase and the ElevenLabs key — every one of which is otherwise unreachable on such a device. `useFocusedField` falls back to the *last* field that had focus, and refuses one that has left the page.
- **QWERTY**, and that is a concession rather than a design. It was built frequency-ordered first — commonest letters nearest the middle, which really is less travel, and travel is what a gaze pointer pays for. What that costs is that nobody has ever seen such a keyboard, so every letter has to be hunted for until it is learnt, on a board somebody is trying to hold a conversation with. Familiarity won. The apostrophe takes the tenth slot of the middle row rather than living behind `?123`: it is in "I'm", "don't" and "it's", and a layer switch either side would cost two dwells every time.
- **Keys never move.** Not between modes, not between layers — shift and backspace flank the short row in *both*, so a pointer that has learnt where backspace is finds it there either way — and above all not in response to what was just typed. A layout that rearranged itself around a prediction would make every letter a fresh search. On the symbol layer, where shift has nothing to do, there is a **gap** rather than a key that answers to nothing: a dead target is only slightly better than a wrong one.
- **Height is the whole design.** Typing narrows the board to what matches, so the point of typing here is to reach a phrase in three letters rather than to write it out — and a keyboard that leaves no board leaves nothing to narrow. Four rows are squeezed into `30dvh`, `42dvh` on a short screen and `26dvh` on a tall one, with the gutters in pixels rather than rem: the keys grow with the text size, the gaps between them need not.
- **Shift is a ring**: one dwell arms it for a letter, a second locks it, a third puts it away — the same shape as the modes on the message box. Two states would leave no way to type a run of capitals; a separate lock key would be a second target where there is room for one.
- **It is portalled and fixed, above the panels**, because most of the fields it has to reach are inside one. `.app` gives up the same height from the bottom rather than being overlapped, so **the emergency bar stays above it** — the one surface somebody reaches for without reading it must not be the one the keyboard covers.
- **It is offered only where it has been asked for.** `settings.keyboard` is off until somebody turns it on in Settings, and the toggle is not in the rail until they do. It is the one way to type at all on iOS and a target in the way on a device with a real keyboard, and a board is somebody's own screen: a control they will never use is one their gaze passes over on the way to the ones they do. **It does not travel between devices** — see `DEVICE_LOCAL_SETTINGS` — for the reason the text size does not: which keyboard a device can raise is about the device, and the same person's tablet and laptop do not answer the same way. Taking it away in Settings closes whatever it had open, or a board would be left with four rows of keys and no way to put them down.
- **The toggle sits beside the menu button** and keeps its place in both modes. It is the same kind of thing as the menu: a surface the whole app shares rather than anything about the message. On a device that cannot type without it, a control that moved would be the worst one to have to hunt for.
- **A key refuses focus on the way down.** A dwell control is focusable, and a key that took the focus would take it off the field the letter is meant for. There is no pointer-down at all on the device this exists for, so that guard is for everybody else.
- **Backspace repeats while it is held**, at `settings.repeatDelayMs`, and `deleteBack` reports whether it removed anything so the repeat stops at the start of the value.
- Keys dwell at `settings.actionDwellMs`, the same as a phrase. **A word is twenty of those**, so a keyboard dwell of its own is the obvious next setting if typing turns out to be slow.

## Everything a dwell can reach

**Nothing in the app answers only to a press, and nothing scrolls that a dwell cannot scroll.** An audit found that neither was quite true, and every gap was one somebody working the board by gaze alone could see and not use. None of them failed a test, because a test that clicks a control proves nothing about whether a rest on it does anything — so `tests/app/reach.test.tsx` rests and never clicks, and `tests/app/structure.test.ts` stops the next gap being written.

- **Three fields took the caret only on a click** — the account keys and the sync passphrase, a category's name, and a spinner's figures. See *Placing the caret*.
- **Four links answered only to a press**: the policy and the terms from the sign-in page and from the guide, and the way back from those pages. `DwellLink` is a real anchor with the dwell hook's own click handler in front of it, so a click in the second after the screen moved is refused there as it is everywhere. **The same tab, always**: a new tab needs a click to be allowed, and a dwell has none, so it would be refused for exactly the people it is for.
- **The legal pages had no way back and no way down.** They scroll in a `ScrollPane` now, and render inside the settings provider — they need no account, but a dwell there should take this person's time rather than the one the app ships with.
- **The slot chooser scrolled by wheel alone.** `{bodyparts}` is fifty words and the chooser is a screen, so most of them were below the fold — on the chooser somebody opens to say which part of them hurts. Its options are in a pane, with the preview and Cancel held either side of it.
- **The edit strip scrolled sideways on a phone** with nothing to scroll it by. It no longer scrolls at all: the title gives way to an ellipsis, and the category trigger never leaves the strip.
- **The two text boxes scrolled past their cap with nothing to scroll them by.** See *Styling*.
- **A focused field drew two lines.** Its own border tints on focus and the app's focus ring drew three pixels outside it, so every field a dwell had put the caret in wore two accent lines. Fixed on the message box first and nowhere else, which left every key, passphrase and figure in Settings doubled. `.caret-field`, the two boxes and nothing else take the ring off and say focus on their own border — `tests/app/structure.test.ts` holds both halves, since taking the ring away without a border to replace it takes the only sign of focus a keyboard user had, which is what happened to the heard box.
- **The file button did nothing to a rest.** A browser opens its picker only for a real press, and a dwell is a timer, so for somebody working by gaze alone this is refused every time — it used to be refused in silence, a label wrapped round a hidden input. It is a dwell control in front of one now, asking through `showPicker` because that is the one of the two ways that *says* it was refused, and naming **Paste a backup** when it is. The input is `aria-hidden` and out of the tab order, so there is one target there and not two.

## Whose board

**A board is the signed-in person's, and nobody else who signs in on the device can open it.** Every account used to share one: the keys were global, so the next person to sign in on a device opened the last one's phrases, lists, keys, Sent list and sync passphrase. `core/store.ts` is the whole of the fix, and `tests/app/accounts.test.tsx` drives it through the screens.

- **Every name is read through `storageKey`**, which puts `@owner` after it — `google:1234`, the provider's own id, or `guest`. `USER_KEY` is the one exception, being who is signed in rather than anything of theirs. `tests/app/structure.test.ts` fails on a read or write that skips it, since a key read under its bare name is shared by every account on the device.
- **The first owner keeps the bare names.** `peri_first_owner` records whoever opened a board first, and their keys carry no suffix — so the board from before this existed goes to whoever was using it, or else to whoever signs in next, **without a byte of it being moved**. A move is several writes and can stop halfway; this is one. Every later owner's keys end in `@owner`, which the bare names never can, so nothing written for one board lands on another.
- **Every guest is one guest.** A guest proves nothing about who they are, so their board is open to anybody who continues as one — the sign-out dialog says so to a guest and not to an account — and never to an account. A guest's board does not follow them into an account either: the guide says to take a backup across.
- **Somebody signed in before accounts had ids keeps the bare names** and does not become the first owner. They have no id to keep a board under, and nobody can sign in as them in the meantime — signing in as anyone replaces them — so the board they had stays theirs until they sign out, and goes to whoever signs in next.
- **Signed out is nobody's board**, `@nobody`, so the sign-in page and a legal page opened signed out read nothing of anybody's. It holds one thing, the sign-in page's settings, and they are carried both ways: **signing out leaves it the dwell times and text size of the board being left** (`leaveForSignIn`), since somebody who needs a slow dwell cannot sign back in at a quick one, and **a board opened here for the first time starts from them** (`settingsOnArrival`), since the dwell control is on the sign-in page precisely so somebody can slow it down before they reach their board. The rest of the settings stay behind — the dwell times say nothing about anybody, their voice and their language might.
- **Signing out reloads the page.** A board is held in memory as well as in storage — the screens, the translations already read, the audio — and a request still on its way writes wherever storage points when it lands. A fresh page is the one way to be sure none of it reaches whoever signs in next, and it is why signing in can simply open the new board: it only ever happens on a page nobody's board was open in. **Another tab signing somebody in or out reloads this one too**, off the `storage` event, or it would go on showing a board that is no longer the signed-in person's.
- **What else keeps something of theirs asks `storageKey` too.** The translations remembered in `core/translation.ts` are read again when the board changes rather than carried over; the audio in `voice/audio-cache.ts` is in a database named the same way, so a factory reset takes one board's clips and nobody else's.
- **It keeps boards apart inside the app; it does not lock them.** Every board sits unencrypted in the same browser storage, which anyone with the browser's developer tools can read — the privacy policy says so rather than letting "only your account can open it" read as more than it is. Nothing checks a sign-in against a server, and a stronger lock would need something that did.
- **`forgetWhoseBoard` is a test seam**, put back by `tests/setup.ts` before every test: the bare names, where a page is before it has opened a board. The app never is — `App.tsx` opens one before anything reads — but every test not about whose board is open reads storage there.

## Settling after the screen moves

**A pointer rests where it last fired.** Whatever arrives underneath gets a `pointerenter` of its own — the browser's doing, not a mistake — so a control that appears under a resting pointer starts dwelling on nobody's instruction. The menu has guarded its own items against this from the start (`REOPEN_GUARD_MS`); `holdDwells()` is the same second, applied where the *whole screen* changes.

- **Two callers, both chosen for being where the screen moves rather than where a control fires.** `PanelBack`, which replaces the panel with whatever is behind it — and the way out of the menu lands on the board, where what is underneath is a phrase that would be spoken. And the `zoom` effect in `App.tsx`, because changing the text size relays out every control on screen around a pointer that has not moved. In `App.tsx` rather than in the settings row, so every route to a new text size is covered: the spinner, its revert, a restored backup, a board arriving from another device. Not on the first run, or the app would refuse to answer for its first second.
- **A tap is guarded exactly as a dwell is, and the keyboard is not.** That is not obvious and it is the whole point: a gaze rig can be set to send a real left click where it rests, so on the device this app is for the click *is* the dwell — the operating system is doing the holding — and a guard the platform walks around is not a guard. It cost a session's debugging to learn, from a report of the board selecting the cell under the pointer after a live re-sort that looked exactly like the guard failing. What it costs in return is a mouse user losing a click in the second after a panel closes or the text size changes, which is the same second their hover dwell is already deaf for. Enter and Space are left alone, because they are aimed by focus rather than by position and focus follows its element when the screen moves. `screenJustMoved` is the single question both routes ask.
- **It stops controls arming and leaves a control already being held alone.** That line is the whole design. Somebody resting on a control is deliberately working it — the text-size spinner is exactly that, and cancelling it would mean a hold that stepped the size once and stopped rather than repeating. What the guard is for is the opposite case, and every one of those arrives through `start`.
- **Once the second passes, a pointer still resting on something stays inert until it moves.** Arming happens on arrival, and it has already arrived. That is the intent, not a shortcoming.
- It is module state, so `tests/setup.ts` clears it between tests: one test going deaf must not leave the next unable to dwell at all.

## When the pointer leaves without saying so

**Safari sends no event at all when the pointer moves to another window.** Not `pointerout`, not `pointerleave`, not `pointercancel`, not `blur`; `:hover` stays true on the element underneath and `document.hasFocus()` never changes. Measured against the macOS Accessibility Keyboard — which floats over the page and is deliberately non-activating, since it must type into the app beneath it — the page went silent for 2.7 seconds and the dwell underneath fired 1.6 seconds into that silence, speaking a phrase nobody had chosen. Chrome sends a `pointerout` with a null `relatedTarget`, which is why it has never shown this and why the shared listener in `ui/dwell.ts` has always been enough there.

Both of the existing cancellations are defeated at once. The control's own `onPointerLeave` is synthesized by React from that same native `pointerout`, so it is not an independent path; and the `blur` listener cannot fire, because a non-activating panel is one that never takes focus.

**So the stream is read instead.** A head- or eye-tracked pointer is a *continuous* device: it emits a `pointermove` every ~33ms for as long as it exists, drifting a pixel or two while its owner holds perfectly still. A mouse is the exact opposite — at rest it emits nothing whatsoever. A pointer that has been streaming and then stops dead has left.

- **A pointer that never streamed is never touched**, and that is the property that matters most: holding back a mouse user's dwell would leave them with no working control to undo it with. Under jsdom no test fires a `pointermove`, so every other test in the suite exercises exactly that path.
- **The signature is continuous movement that *goes nowhere*.** Continuity alone is not enough — a mouse crossing the screen is continuous too, and covers ground; a mouse at rest covers no ground but sends nothing. Only a tracker does both at once. Twenty moves inside 1.5s, none more than 120ms apart, averaging under 3px each.
- **It is a claim about a device, so it expires.** Ten seconds after anything last looked like a tracker, nothing is claimed — a tracker unplugged in favour of a mouse must not leave every dwell held back for good.
- **Movement is the only way back.** Nothing fires when the pointer *returns* either: the browser never noticed it leave, so the element is still `:hover` and no `pointerenter` is coming. A held-back control arms again on the next `pointermove` over it, which is why `onPointerMove` is in the props at all — and why it is guarded, since a streaming pointer resting on a control would otherwise re-arm it thirty times a second.
- **The repeat is checked on every tick**, not only at the first firing. A repeating control left running by a pointer that has gone is the worst version of this, because it does not stop — a scroll arrow reaches the end of the grid, a spinner drives the text size to its limit. A tick landing inside the 150ms threshold still fires; at a repeat faster than that, exactly one does.
- **150ms is provisional.** It is twelve times the observed 33ms cadence and it suppressed the measured failure with 1.2 seconds to spare, but it was picked against one device. `tools/pointer-probe.html` is what to tune it with: leave it open through a session of ordinary use and read the **largest gap** — that is the number `STALL_MS` has to sit above — and use its *block the main thread* buttons for the one thing that could make a present pointer look absent.
- Like the settle guard it is module state, and `tests/setup.ts` clears it between tests.

## Saying when something failed

Every service call in this app is written so that failing changes as little as possible: sync fails into a line of text under a setting, a translation fails into the words as they were written, an ElevenLabs voice fails into the device's, a service worker that will not register leaves an app that still runs. That is the right behaviour, and it is exactly what makes these failures invisible — **a board that carries on working looks like a board with nothing wrong**, and the first question anybody debugging one has is what the service actually said.

`reportFailure(where, what)` in `core/report.ts` is the one shape they all take: `[Peri] sync/pull: Server said 500`. `where` names the thing that failed the way the source tree does, so the console can be filtered and the code grepped.

- **Never the words, and never the key.** What goes in is the operation and the failure Peri would already show a user — a status code, a refusal, "could not reach". A phrase belongs to the person who wrote it, and a console ends up in every screen-share and bug report from then on; a key in a console is a key in a screenshot. `tests/translate/client.test.ts` holds that line.
- **Only what is actually a fault.** A 409 from sync is somebody else writing first, which the next poll reconciles — no warning. A parser refusing a damaged backup, a `localStorage` read finding nothing, `Intl.DisplayNames` missing: all of those are defined paths with a defined answer, and warning about them would fill the console during normal use. A *write* that fails is different, and does warn: it means data was lost.
- **Tests capture Peri's own warnings and pass everything else through.** `warnings` in `tests/setup.ts` collects anything beginning `[Peri]` — nearly a thousand tests drive these paths deliberately — while React's warnings still reach the terminal, which is the whole point of having them.

## Waiting

`BusyIndicator`, fixed in the top corner, for the two things that can keep somebody waiting: an exchange with the sync server (`sync.status === 'working'`) and re-parsing the phrase table after an alias list changes (`board.rebuilding`).

- **It waits 250ms before saying anything.** Both of those are usually over in a few milliseconds, and a spinner that appears for fifty of them is a flicker — which costs more here than anywhere else, because **the pointer is the user's gaze**. Something that catches the eye does not merely distract; it aims. Going *off* is immediate: the delay exists to swallow flickers, not to leave one on screen after the work is done.
- **It is not a control.** No dwell, no target, `pointer-events: none`, and a gaze crossing the corner of the screen finds nothing there. A dwell user has no way to dismiss something that catches one.
- **The rebuild is a transition.** `useTransition` in `use-board.ts`, so the indicator is painted before the parse rather than after it — a synchronous `useMemo` would finish the work before the screen could say it had started.
- **It sits above the panels** (`z-index: 600`), because both things it reports on are started from inside one: Synchronize lives in the settings panel and the rebuild is triggered from Aliases.

## Settings

Six numeric values, a spoken language, a voice, and a linked account. **`keyboard` is whether Peri offers its own keyboard**, off until it is asked for — see *Peri's own keyboard*. **`zoom` is the text size**, and it works by being the root font-size: `App.tsx` writes `${zoom * 100}%` onto the document element, and every size in `index.css` is in `rem` so all of it follows. A percentage rather than a pixel count, so it multiplies whatever the reader has already told their browser they want. It is deliberately not a browser zoom — that scales the whole page, which on a board fixed to the height of the screen means fewer phrases and more scrolling; this grows only what is read. `tests/app/structure.test.ts` fails on any `font-size` left in pixels, in the stylesheet or in a component's inline style, because one left behind is a line that will not grow for the person who needed the setting. **Changing it makes the app deaf for a second** — see *Settling after the screen moves* — and **it does not synchronize**, along with `volume`. **`autoSpeak` ships on and is not carried across a load** — see the modes under *Editing a phrase*. It is stored like the rest and ignored on the way back in, so the board opens ready to talk however it was left: a board that cannot say anything the moment it is switched on is not recoverable the way a mode two dwells away is. That is why `readSettings` falls its missing case back to the default rather than to `false`, and why every test about composing switches out of auto-speak after rendering rather than seeding it off. Three things about putting them back:

- **The label beside a spinner's figures is as wide as the widest thing it can say**, never narrower and never changing. It was 32px, which cut `1000ms` to `1000r` and ran `100%` into the + beside it. Fitting it to what it says *now* would move the + and the reset every time the value crossed a digit, and those are aimed at by position — so `SettingSpinner` writes every value in range once, keeps the widest, and draws it invisibly in the same grid cell as the real value, out of the text so a screen reader and a test both read the value alone. It is also never narrower than a time, `6.5ch`, so the + and the reset line up down the whole list rather than each row's sitting where its own widest put it.
- **Every settable value carries a revert**, at the end of its spinner, which goes quiet at the default rather than away — a row that changed width as a value crossed its default would move the two buttons beside it. `SettingSpinner` takes `defaultValue` **in the units it displays**, so Volume and Speed scale theirs the same way they scale `value`. `ResetIcon` is a closed loop, deliberately not the open hook `UndoIcon` draws: undo means "put back the last thing I did" — the message in the topbar, a deleted word in the Aliases panel — while reset means "put this back to how it shipped", and the two must not be learnt as one control.
- **Reset to Factory Defaults takes everything of this person's**, not just the settings — phrases, categories, the emergency arrangement, details, the sent list, the linked account, the audio. **Nobody else's**: another account's board on the same device is not this person's to take away. So it asks first, in a dialog **portalled and centred** for the same reason the Sign-out one is, and the first thing that dialog offers is a backup to keep. It **leaves the user signed in**: signing out is its own item with its own confirmation.
- **The reset clears storage and reloads.** Nothing in the panel can reach the React state holding the same values — the board, the composer, the sent list, its own account row — and a screen still offering phrases that no longer exist is worse than no reset at all. `RESETTABLE_KEYS` is a list rather than `localStorage.clear()`, because the origin may hold something Peri did not put there; a key added to the store and forgotten there is a key the reset leaves behind.

## Synchronizing

Off until somebody turns it on, and then two devices signed in to the same account keep the same board. **What is on the server is ciphertext and an address, and neither can be connected to a person.**

- **The payload is a backup.** The same document `buildBackup` writes and `applyBackup` reads — already a diff against the phrase table, already versioned, already tested against damage. Built with `SYNC_EPOCH` rather than today, because `buildBackup` stamps the moment it ran and a stamp that moves every render is a board that looks edited every render; the device would push for ever. When it was written down is `Snapshot.updatedAt`.
- **One passphrase does two jobs.** PBKDF2 (310k, SHA-256, salted with the account) gives a master; HKDF expands it into the AES-GCM key *and* the 64-hex address the blob is stored under. So **the address is the credential**: a server that has it cannot derive the key, and somebody who does not know the passphrase cannot even find the blob. The alternative was keeping an OAuth token on each device and verifying it server-side — a stronger door, at the price of long-lived provider tokens in `localStorage` on a device left in a day room.
- **What that leaves open, and it is written in the function's own header:** anyone who learns an address can read the ciphertext and overwrite it, and writes are capped by shape and size and nothing else. The revision is optimistic rather than atomic — Blobs has no compare-and-swap — and the loser of a race reconciles on its next poll.
- **The last change wins, whole.** Not field by field: a board is a diff, and half of one merged with half of another is a board neither device ever had. Merging is what the *import* screen does, because a file from somebody else must never delete a phrase — but between your own devices a deletion has to travel, or the feature is a machine for resurrecting phrases you just threw away. What it costs is stated in the guide rather than hidden.
- **The first exchange is the exception, and it is the one moment sync will not decide by itself.** Clocks are worthless there: a device joining an account carries an `updatedAt` from whenever it was last edited, which may be years after the board it is joining. So — nothing on the server, this device publishes; nothing of the user's on this device (`hasOwnBoard`), it takes what is there silently; **both**, and it asks, in the settings row, and touches neither board until answered. `joined` is what remembers, and turning the setting off and straight back on with the same passphrase is not a join.
- **The passphrase can be read back off the device that has it**, and so can the ElevenLabs key — `SecretField` in the settings panel: hidden by default, **copyable without ever being shown**, and shown only on a second deliberate act. The two controls are **icons** (an eye and a copy), because the field beside them is the widest thing in the panel and two labelled buttons pushed it down to nothing on a phone — but the name stays on each, since an icon says nothing aloud and these are the two controls where the wrong one puts a credential on a shared screen, because this panel spans the viewport and these are set up in rooms with other people in them. It does not re-hide itself on a timer: somebody reading a passphrase out to whoever holds the second device needs it to stay put. The key was write-only until this existed, and ElevenLabs shows one exactly once.
- **A mistyped passphrase is silent by construction** — a different address is a different board, so nothing arrives and, the part that matters, nothing is overwritten. That is indistinguishable from sync being broken, which is why the row shows a six-character **code**: two devices showing the same one agree.
- **Text size and volume do not travel.** They are about the screen and the speaker in front of somebody — a phone at arm's length and a tablet on a wheelchair mount want different numbers, and it is the same person — while dwell times are about their motor control and the voice is how they want to sound. `DEVICE_LOCAL_SETTINGS` names them, `portableSettings` blanks them on the way out and `keepDeviceSettings` keeps this device's own on the way in. **Blanked as well as ignored**, so that turning the text size up is not a change to the board at all: left in, it would count as news, push, and arrive on the other device as "Board updated from your other device" — a notice about something that did not happen. **A backup still carries both**: restoring one is putting a device back the way it was, which is a different question from keeping two devices that are in use at once alike.
- **The linked ElevenLabs account travels with the board**, in `Snapshot.account` and never in the backup document — see the Voices section for why those are different questions. It is what makes a phrase given an ElevenLabs voice on one device still sound like itself on the next, since `settings.voiceURI` already travels and used to arrive naming a voice the receiving device could not fetch. **Three states, not two**: an account, an explicit `null` meaning unlink, and *absent* meaning a snapshot from before this existed said nothing — and silence must not be read as an unlink, or one device on an older release strips the account off all of them. The account is compared before it is written, because `setAccount` empties the audio cache and doing that on every poll would refetch a board's worth of audio.
- **The account is held in `talk.tsx`, not in the settings row that edits it.** It is part of what sync sends, and a row holding its own copy goes stale the moment a board arrives carrying a different one.
- **The passphrase and the flag are never in a backup, and never in a snapshot either** — unlike the ElevenLabs key, which travels in one. The passphrase *is* the lock on the snapshot, so putting it inside is circular; and a restored file must not switch a stranger's device on and start it writing to a server. It lives under `peri_sync`, outside the three things `buildBackup` reads.
- **Nothing throws.** A board works offline; a device that cannot reach the server has lost nothing and carries on exactly as Peri always has.
- **Three documents have to agree** about what leaves the device: the Synchronize row in Settings, *Keeping two devices the same* in the guide, and the Synchronizing section of the privacy policy. Change one and change all three — the same rule the ElevenLabs disclosure follows.

## Speaking another language

**The board stays as it was written; what comes out is translated.** Somebody goes on reading their own phrases in their own words, and a listener who does not share that language hears it in theirs. That is why translation sits in front of `speak()` rather than anywhere near the grid — and inside it, for the reason stripping markdown is: every route to the synthesiser would otherwise have to remember.

`settings.language` is the trigger. Empty, or plain English, means no translating at all.

**A tag is not enough once regions are involved.** Three questions hide inside one — what to *say it as*, what to *translate it with*, and which shipped table it reads — and `VARIETIES` in `core/translation.ts` is where they get three different answers. Anything not listed there answers all three from its base language, which is right for `de-DE` and wrong for both of these:

- **Spanish (Puerto Rico)** is `es-PR`, said as `es-PR`, read from `es-419.json` and asked of the service as plain **`es`**. Nobody has a Puerto Rican target, and Google's `es-419` is on the LLM model, which wants a service account rather than a key and so cannot be called from a page. **The regional wording lives in the shipped table**, which is named for the variety rather than for a provider's code — the provider has changed once already. European Spanish would give a board `vosotros` and `coger`, the second of which means something else entirely in San Juan.
- **Jamaican Patois** is `jam`, said as **`en-JM`**, and has **no target at all** — Google Translate the product added Patois in 2024, but Cloud Translation, the one a page can call, carries Haitian Creole and no other English-based creole. Patois is a language rather than an accent, so this is the case the shipped tables exist for: the phrases Peri comes with are written out ahead of time, and anything somebody writes themselves is spoken as they wrote it, because there is nowhere to send it. **`translationTarget` returning null is load-bearing** — asking anyway would hand back English and call it a translation, which is worse than not translating. It is guarded twice, in `speak` and in the client, and the two are tested apart: the client refuses to ask, and `speak` says the words *in the same tick* rather than deferring them to a translation that can never come.
- **There is no Patois voice on any device**, which is why the tag the synthesiser is told is not always the tag the setting holds. Patois written down is close enough to English orthography that an English voice reads it about right, and a Jamaican one better.

Two sources, in order, and then a fallback:

- **The tables Peri ships** — `core/imports/translations/<table>.json`, named for the *table* rather than the tag (`es-PR` reads `es-419.json`), keyed by the exact words that would be spoken, lazily loaded for whichever language is chosen and held in memory. Instant, offline, free, and **already in hand when the emergency bar is pressed**.
- **What has been translated on this device before**, under `peri_translations`. This is where a phrase somebody wrote themselves ends up, and a composed message with it.
- **Google Cloud Translation**, for anything in neither, once each — and only with a key.

Six things follow from that, and each has a test:

- **The lookup is synchronous.** `translationFor` returns a string or nothing; it never returns a promise. The emergency bar speaks the moment it is pressed, and a promise there is a phrase that arrives after somebody needed it. That is also why the shipped table is loaded when the *language* changes rather than when a phrase is spoken.
- **Never silence, and the original is not silence.** A phrase that cannot be translated — no key, no network, the service refusing — is said as it was written. A listener who has to work at it is recoverable; nothing said at all is not.
- **`instant` never goes to the network**, exactly as with a voice. The emergency bar says what it already has in the chosen language, and everything else in the original, immediately either way.
- **Markup comes off first**, so `**Help me!**` and `Help me!` are one translation rather than two that never match — the same reason the audio cache is keyed after stripping.
- **A phrase carrying a slot is not in the shipped table**, and that is deliberate: what gets spoken is not known until the blank is filled, so a translation of `Please turn {control} the lights` would never be looked up. Those go to the translation service like any phrase somebody wrote.
- **The six emergency phrases are hand-written in every table, and never generated.** They are not in `phrasetable.json`, so the tool cannot produce them — it *merges*, which protects them where a file already exists and gives a brand-new language none at all. Vietnamese arrived that way: 2,106 phrases and an emergency bar that fell back to English, silently, because nothing threw and the test named `['es', 'fr']`. `tests/core/translation.test.ts` now reads the directory, so the next language cannot ship the same way. A new table starts by copying the six out of `jam.json` and translating those by hand.
- **The shipped tables are built, not fetched.** `tools/translate-table.ts` writes them once per language, they are committed, and they are read before they are committed. It takes the tag Peri stores rather than the code the service wants, so the mapping lives in one place instead of in somebody's head at the command line — and it **refuses a language nothing translates into**, naming the file a person has to write by hand instead. `tools/` is in the typecheck for that reason: it imports `core/translation.ts`, and a tool that disagrees with the app is worse than none.

**The key is the app's, not the user's** — `VITE_GOOGLE_TRANSLATE_KEY`, out of `.env.local` in development and the site's environment on a deploy, inlined by Vite. So there is nothing in Settings to fill in, nothing in a backup, and nothing in a snapshot: no device holds a translation key, which is the whole of why those three questions no longer arise. It was a field in Settings, and asking somebody who communicates by gaze to open a Google Cloud account before their board can speak Spanish is not a setting, it is a wall — the ElevenLabs key stays theirs because it bills them for a voice they chose. What *is* still on the device is what has been translated, and that is a record of what somebody actually said, like the Sent list: never in a backup, and rebuilt for nothing.

### The Translations tab

A tab pinned at the very end of the category bar, holding what has been said in another language, newest first. `talk/use-translated.ts` is the hook and `core/store.ts` holds the record.

**Why it exists at all:** the board stays in the user's own words and the translation is what comes *out*, so until this there was nowhere to see what had been said and no way to say it again without going back through the service and paying for it twice.

- **It is not a category**, and the two properties the request named are why. `TRANSLATED_FILTER` begins with a space, exactly as `SENT_FILTER` does — names are trimmed before they are saved, so no real category can collide with it — which is what lets it be **pinned last** where a custom order cannot reach it, and **always newest first** where the order control cannot change it. A real category would be renameable, movable, deletable, and in every backup.
- **A cell draws the translation with the board's own wording under it**, in the muted grey. Without the second line the tab is a wall of text the person using the board cannot read: every other surface here is in their own language and this is the one that is not. `Phrase.detail` carries it, and it is absent everywhere else — `PhraseCell` is memoised over a couple of thousand of these. The accessible label reads both halves, and the second line is `aria-hidden` so a screen reader does not say the phrase twice.
- **An entry belongs to a language as well as to a phrase.** The same words said in Spanish and in French are two entries; said twice in Spanish, one. **The tag, not the table** — `es-PR` reads the `es-419` table and is spoken as `es-PR`, so the table could not say which voice to use or what to call it.
- **The order *is* the recency.** No timestamp, for the reason the Sent list keeps none: a list held newest-first already answers the only question asked of it.
- **Saying one again does not translate it again.** `SpeakOptions.alreadyIn` is what says so — the words are said as they stand, in that language. Without it the service would be asked for Spanish from Spanish, and, the part that shows, the Spanish would be filed as a translation of itself and the tab would grow every time it was used.
- **It is said in the voice remembered for that language.** `voicesByLanguage` already holds one per language, and a cell here was recorded while the board was set to that language, so the voice chosen under it is the voice it was heard in.
- **`speak` reports what came out, and only when something really was translated.** `onTranslated` fires on the two paths that translate — the shipped table or the cache, and the service — and on none of the three that fall back to the words as written. A phrase spoken as it was written is not a translation, and an entry claiming otherwise would be wrong in a list somebody reads. It hands back the **stripped source** alongside, so no caller has to strip it again and end up disagreeing about what was translated.
- **A callback rather than a write from inside `speak`**, because the caller decides whether it counts. A phrase chosen off the board and a message sent both do; a voice sample in the picker and **the emergency bar** do not — that surface exists to not wait on anything, and a storage write on the way to saying "Help me!" is exactly what it must not pick up. Same line the usage record draws, for the same reason.
- **Nothing in it counts towards how much a phrase is used.** Those ids name a translation rather than a phrase on the board, so counting them would fill the record with ids that can never match anything and never fall out — the rule Sent already follows.
- **In edit mode the bin forgets and Save keeps.** Both work exactly as they do under Sent, and `draft.kept` is what names which record a phrase came off, because all three labels said "message" until there was a second one. **A kept translation is an ordinary phrase**: its language is not carried over, since a phrase on the board is spoken in the language the board is set to and a phrase that quietly ignored the setting would be the one exception nobody could see.
- **It is never in a backup and never in a snapshot**, under its own key, for the reason the Sent list and the usage record are not: it is what somebody actually said, and a backup is a file made to be handed to somebody else. It is in `RESETTABLE_KEYS`, and `tests/core/backup.test.ts` holds it out of the file.
- **Three tabs are not categories now**, two pinned at the front and one at the end. `canArrange` is false for all three, the order control goes quiet on two of them, and the quiet label names the tab rather than naming All — there being three tabs it could be.

## Listen mode

Peri has always been one-directional. Somebody chooses phrases and the board says them; the person they are talking to speaks into the room and leaves no trace of it anywhere. Listen mode writes that half down: a microphone at the message box's **upper-left corner** opens a second text area above the message, holding the question that was just asked.

The three corners of that border are now all spoken for, and each holds a different kind of thing: a mode in the middle, a value at the right, and at the left the one control that opens a surface of its own.

**The control is drawn as a question mark, not a microphone**, and the box waiting on it says *Speak or type a question* rather than *Listening…*. A microphone says how the words arrive rather than what they are, and they do not only arrive that way — the box takes a question typed as readily as one heard. What the glyph gives up is the universal *this is recording* cue; the disclosure of what the browser does with the audio was never resting on it, and is in Settings, the guide and the privacy policy as before. The guide's `:listen:` mark draws the same glyph, and `tests/app/listen.test.tsx` holds the two to one picture. The code still calls the control the microphone, because that is what it opens.

**The *this is recording* cue lives on the question box instead**: a live microphone, `.heard-live`, at the right end of the box's lower border, drawn while `heard.hearing` is true and at no other time. **`hearing`, not `listening`**: `listening` is the session, which opens when it is asked for, while `hearing` runs from the recogniser's `audiostart` to its `audioend` — after the browser has been given the microphone, and over before the session is. A light keyed on the session said the microphone was live while a permission prompt was still up. The box being open is not the microphone being on either — the recogniser stops by itself when somebody stops talking, and clearing the box starts it again — so the light answers the question the question mark cannot. Four things about it:

- **Not a control.** There is nothing to do to it that the tools beside it do not already do, and a target that did nothing would be a dwell spent for nothing: a `span` with `role="img"`, and `pointer-events: none`.
- **Only a level inside the capsule moves.** `MicIcon live` fills the capsule with `.mic-level`, scaled from its foot in uneven steps as a voice meter rises and falls; the ground under it is solid and carries no glow. It was a pulse first, the whole light brightening and dimming, and that did not work: the ground dimmed with it and the box's border showed through, and the glow lay on the border, so the border itself seemed to pulse. Under `prefers-reduced-motion` the level stands still, part full.
- **In the row of tools, not positioned over the corner.** `margin-left: auto` puts it at the right end, and a box too narrow for all four — the wide-screen split at a large text size — pushes it along rather than laying it over a control.
- **The guide and the privacy policy both show it**, as `:mic:` — the same outline standing still, with no level — and `tests/app/listen.test.tsx` holds the three to one glyph.

**The box takes nothing without an Anthropic key it can use.** It is for getting answers, and the answers are the user's own account, so with no key — or one Anthropic turned away with a 401 or a 403 — it says so and where to go, as its own read-only words (`KEY_NOTICE`, in `use-listen.ts`), and listens to nobody. As its words rather than as a placeholder, so the topbar measures it like a question and the box grows to hold all of it. A refusal is held against the key (`refusedKey`) rather than as a flag, so a new key — set here, or on another device and synchronized — lifts it without anything remembering to. **Keys are checked before they are saved**, by listing Anthropic's models, which costs nothing: `checkReplyKey`, the ElevenLabs link's shape, and nothing is saved that could not be checked.

**Typing stops the microphone.** `correct` stops the recogniser and bumps the question, so nothing it hears on its way out is written over the typing and nothing it had heard is answered by itself — a typed question is asked about when somebody asks.

- **Beside the message on a wide screen, above it on a narrow one.** Stacked, opening listen mode pushes the grid down by the whole of the heard box and the tools under it — a row of phrases on a short screen, and on any screen the surface somebody is actually speaking from. A wide screen has width nobody is using and no height to spare, so at `WIDE_ENOUGH` the two boxes share the line: **35% question, 65% message, 2rem between them.** Both of those are dwell targets and 2rem is this app's target-separation number rather than a spacing one, so it is written as the flex gap, which does not shrink. The heard box is capped there against `--message-max-height` less its own tools, so that the column ends where the message box alone could and **opening listen mode costs the board no height at all** — capped by something it must be, since there are no dwell controls on that box and what scrolls out of it is out of reach. **Neither strip on the border moves**: both are positioned against `.text-display-wrap`, which is the same size in the same place either way, so the microphone stays at one point on screen and merely rides a different box's corner. It is the way out of listen mode as well as the way in. **One breakpoint, not two** — `topbar.tsx` asks the same question in JavaScript for the two pickers, which are not cheap to mount and hide, and `tests/app/structure.test.ts` holds the two together.
- **Opening it puts the board in auto-speak.** Somebody has just been spoken to and is about to answer, with a person waiting in front of them — which is the whole of what auto-speak is for, and the alternative is a board that hears a question and then wants a second dwell somewhere else before it can say anything back. The same bargain the automatic asking strikes: the dwell it saves is the point. **Only on the way in** — closing the box leaves the mode exactly as it is, a conversation that has ended being no reason to stop talking, and a control that undid itself on the way out would take away a mode somebody had chosen in the middle of one. It takes the board out of edit mode as a consequence, those two never being on together, which is right rather than incidental: a question in the room is not a moment to be rewriting phrases, and what it costs is the blank draft dwelling on auto-speak itself would have cost. The rule lives in `talk.tsx` beside `setMode`, which is why the microphone control takes an `onToggleListen` from the screen rather than calling `listener.toggle` straight — the hook knows about microphones and nothing about modes.
- **Its dwell fill is painted, not sized.** `boxDwellFill` animates `background-size`; `dwellFillH`, which every other control's `.dwell-bar` uses, animates the element's own `width` — right for a bar inside a control and, on a box with nothing inside it to be the bar, the box itself collapsing to nothing and growing back under the pointer resting in it. It flickered, rewrapped its text and re-measured both boxes all the way, and the fill never showed at all. `tests/app/structure.test.ts` now also holds every `animation` to keyframes that exist, which is how the rename that fixed this nearly took the Aliases panel's fields with it.
- **It is a text box, so it answers to a dwell like the other one.** A recogniser mis-hears names, and the one thing a gaze user could never do about that was put a caret in the middle of a sentence. `selectOnHold` is on, for the reason the Aliases panel's fields have it: this box is opened in order to correct something, so a rest on it is intent. **No `onPlace`**, unlike the message box — the caret that hook reports is the composer's and it decides which word the grid narrows to, and a caret moved about in somebody else's question must not reach it.
- **The question is the message box's twin.** Same type — `font-size`, `font-weight`, `font-family`, `line-height`, held equal by `tests/app/listen.test.tsx`, four declarations in two rules two hundred lines apart that a diff shows nothing of — and same padding, same floor, same cap. It was a third smaller with tighter padding, which made a hierarchy out of what is really two halves of one conversation, and the question is the half the person using the board did not write and has the most trouble following.
- **The two boxes are one height, and whichever holds more decides it.** Both grow with what is in them: neither has a dwell control for scrolling and nothing to hang one on, so what a fixed box cuts off is out of reach. Side by side, two boxes of somebody's speech at different heights read as two unrelated things rather than as one exchange — the question is not a caption on the answer. `topbar.tsx` measures both, which is why the heard box's ref is made there rather than in `HeardBox`: the bar is the only thing that can see the pair. **Both are cleared before either is measured**, since `scrollHeight` includes whatever height a box is already holding and one still standing at the other's would report it straight back. `--box-max-height` is the cap on both, and one number on purpose — a pair kept equal by measurement but capped by two numbers comes apart at exactly the point one of them fills up. **Stacked, each is clamped to a fifth of a short screen**, which is the share the question alone used to get: equal heights mean a third each is two-thirds of the screen spent on a topbar. Written as a clamp *on* the cap rather than as a second value for it, and taken off again on a wide screen where the pair spends width instead. The selectors match only while the question is on screen — the heard box being in the document is the condition, so no class has to say so.
- **Interim results are on.** A box that stays empty for four seconds and then fills is indistinguishable from a box that is broken, and this one is watched by somebody who cannot ask whether it is working.
- **The recogniser is told the tag the synthesiser would be told**, `speechTag` again: there is no Patois recogniser any more than there is a Patois voice, so Patois is listened for as Jamaican English.
- **Two controls riding the box's lower border, each offered only where there is something behind it.** Empty it; suggest a reply. **There was a third, which read the question in the board's own language under the words that were said, and it has been taken away**: a translation of somebody else's question is not what the box is for, and the model reads a question in the language it was asked in just as well. **There is no control for the microphone**: clearing the box starts listening and undo stops it. Emptying this box has one reason behind it — what came back was wrong — and what somebody wants next is to be listened to again, so a row with a listen button in it asked for two dwells out of one intention. Opening the box clears the undo stack, since that is a box with nothing behind it. **The first is the message box's own two glyphs** — one box is what somebody is being asked and the other is what they are about to say, and a control meaning *empty this* has to look the same on both or it is two controls to learn. It is the gesture most worth being able to take back here: a recogniser mis-hears, the answer to a question that came out as nonsense is to empty the box, and what that throws away is the only copy of what was said to somebody. A one-step toggle like the composer's, and **listening again clears the stack** — that is a box filling with something new rather than one emptied on purpose, and an undo reaching past it would put back words nobody is talking about any more. On the border rather than in a row beneath it, so the box costs the board the height of a box and not the height of a box and a toolbar — which is worth more here than on any other strip, since what is underneath is the board somebody answers the question from. `.heard-tools` is pulled up by half its own height *and* by the column gap it no longer sits below, both named on `.heard-wrap` so the pull cannot come apart from what it is pulling. Stacked, the half that hangs down meets the mode strip standing up off the message box, which is what `row-gap: 2rem` on `.text-display-wrap` is for — and the stacked height is what it was before, the row they used to sit in having been taller than the half of one that hangs into the gap now.
- **There is no setting for which microphone, or for how loud it is.** Not an omission: `SpeechRecognition` takes no device, no stream and no gain, so it hears whatever the operating system and the browser's own site settings call the default. A picker listing the inputs would move a control that steers nothing, which on a board aimed at by gaze is worse than no control. `tools/mic-probe.html` is what that claim was measured with rather than assumed, and is what to re-measure it with if a browser ever changes its mind.

### The suggested answers

The riskiest thing in this app. A machine offering words for somebody to say is one step from a machine deciding what they meant, so everything is arranged around one rule:

**A suggestion is never spoken.** Up to twenty answers land **on the board**, as cells to read, choose between or ignore; the one chosen goes into the message box, and is said only when the person dwells on Speak — the same dwell every other message needs. Nothing in `listen/` reaches the synthesiser. `tests/app/listen.test.tsx` asserts it **with auto-speak on**, which is the mode where every other cell on the board is spoken the moment it is rested on, and it asserts it twice: of the answers arriving, and of the dwell that chooses one.

**Twenty rather than one, and that is the whole shape of the feature.** One reply put a stranger's sentence in the message box and left somebody to accept it or start again by spelling; twenty fill the surface they already choose everything else from, and the one they rest on is a choice they made. It is also what makes the safety rule affordable — a set of options is not a machine deciding, whatever is in it.

- **They are phrases, not a kind of their own.** `talk/suggestions.ts` turns each answer into a `Phrase`, so the grid, the search, the blank a gap becomes, the caret landing in it and the screen reader's label are all work the board already does. A gap is **a slot with no options** — the app's own blank — rather than three underscores drawn on a cell, which is why `composeWithBlank` puts the caret in it exactly as it does for a fill-in-the-blank phrase off the grid.
- **They are a pinned tab, third, from the first question answered on.** `SUGGEST_FILTER` begins with a space, as Sent and Translations do, so no category anybody makes can collide with it; `canArrange` is false, the order is fixed, nothing in it is counted towards how much a phrase is used, and it is never in a backup or a snapshot. Sent and All keep the places they are found in without looking; what gives way is the first category.
- **The most recent answers are kept until newer ones replace them.** Not listening again, not a correction, not closing the box: each of those used to clear them, on the grounds that answers to a question no longer on screen might be taken for answers to the one that is, and what that cost was the answers themselves — gone the moment the next person spoke or the box was put away, when somebody may well have wanted to go back to one. **The risk is real in one window, and that window is covered**: while newer answers are being asked for, `listener.suggestions` is empty and the tab shows the waiting line, so nothing from the last question can stand in for the next. Held back rather than thrown away, so a request that fails puts the last answers straight back. `askedForRef` is set only alongside the answers it names, so a choice among kept answers is written into the conversation against the question they answered rather than the one that failed. A correction also clears `asking`: it abandons whatever was in flight, and a waiting line left standing promised answers that never came while hiding the ones there were.
- **They survive a reload**, under `peri_answers` — `loadAnswers` and `saveAnswers` in `core/store.ts` — because a board on a mounted device is reloaded by whoever charges it rather than by the person using it, and answers that went with every reload went at somebody else's say-so. **The day's rules, because they are the day's conversation**: forgotten after the same day the questions are, forgotten with them by *Forget today's conversation* and by removing the key, never in a backup or a snapshot, cleared by a factory reset. Five things about it:
  - **Stored as the words, not as phrases**, with the question and when they arrived. How a gap is drawn can change between releases, and a stored `Phrase` would be drawn the old way for a day.
  - **The day is enforced on the screen, not only in storage.** Reading back drops a record a day old, but a tablet on a wheelchair mount can stay open for a week, so a timer takes the answers off the board when their day is up — or "forgotten after a day" would be true of storage and false of what somebody can see.
  - **Only with a key.** Nothing is restored without one, and the render that sees the key go takes the answers off the board — a key removed on another device and synchronized here included. It is the adjust-during-render pattern rather than an effect, which the lint config forbids for a state write, and which would have left a frame of answers on a board with no key behind them.
  - **Forgetting the conversation is the screen's job, not the Settings row's.** The row used to empty storage itself, which now would have left the answers standing on the board until the next reload; it calls `onForgetConversation` from `talk.tsx`, which empties both. `forgetReplyContext` takes the stored answers with the questions, so every caller of it forgets both.
  - **The policy said an answer you did not choose is not kept.** That is no longer true, and what it now says is the part that still matters: of the answers, only the ones chosen are ever *sent* anywhere.
- **The board goes to them, and comes back afterwards.** A tab somebody has to find first spends the seconds this exists to give back, so the screen switches as the question goes off to be answered — the waiting line then stands where the answers will land rather than in a message box nothing is going to arrive in. When the question is done with — the box closed, or a request that brought nothing back and left nothing kept — the board goes back to the tab it was on rather than to All. **It keys on the asking, not on there being answers**: those outlast the question now, so their being there says nothing about anybody being asked anything, and opening the box again must not take the board to answers nobody is waiting for. Every move changes every cell under a pointer that has not moved, so each holds the dwells (`holdDwellsUntilMoved`) — the tab changing in one effect, the answers landing in a second after `showingSuggestions` — and the first returns early when nothing moved, or the board would be deaf on the first render, which `tests/app/App.test.tsx` catches.
- **A typed word does not narrow them.** `filterWord` is empty on that tab for a sharper version of the reason it is empty in edit mode: the answers are alternatives to one question rather than completions of a word, and choosing one puts its words in the box — so the word at the caret would be a word of the answer just taken, and the other nineteen would vanish at the moment somebody wanted to compare them.
- **It never writes over words somebody already had.** The composer's undo is a one-step toggle rather than a stack, so an answer that replaced a half-written message could not be walked back past it. Nothing is asked for at all while there are words in the box — a message half written is how somebody says they are already answering — and the one chosen goes in through `propose`, which pushes the box's history, so an answer taken by accident is one dwell back and a second answer replaces the first rather than piling on it.
- **What is remembered is the answer they took**, not the one the model put first: `chose` is called where a cell is chosen and writes the turn, and a question answered off somebody's own board leaves nothing behind at all. The old single reply was written down whether or not anybody said it, so a conversation could carry on from words nobody had spoken. `chose` and `forgetSuggestion` are stable across a question changing, because both reach a couple of thousand memoised cells.
- **The brief is a list of limits rather than an instruction to be clever**: short answers, first person, no preamble, one to a line. **The exception is expertise, and it earns its place**: the answers are written as somebody expert in whatever the question is about — the medicine, the law, the car, the league table — because the person answering cannot add the sentence the machine left out, every correction costing them a letter at a time, so a vague or hedged answer is not a starting point they can improve but the whole of what they get to say. Bounded twice: **knowing the subject is not talking like one**, still two sentences of the plain words they would have used and never a lecture, and **expert in the subject, never about them** — an expert tone is exactly what would make an invented claim about somebody believed. **The line that matters is about *whose* facts** — a board answering "yes, I took them at eight" to a question about medication would be putting a clinical claim in somebody's mouth. It was written as facts in general at first, which a model reads as covering the capital of France, so it dodged questions nobody could come to harm over and the whole thing read as broken rather than careful. **The world it may answer for, the person it may not.**
- **It is told what day it is.** A bare API call carries no clock, so every question with a *when* in it was answered out of training data as though the year had not moved — not refused, which would at least read as a limit. Taken off the device, since that is the clock the person being asked is living by.
- **It may search the web, once.** Anthropic's own server-side tool, bounded to a single use: this is the one capability here that costs seconds somebody is standing in front of them for, so the model decides whether it needs one at all and a question it already knows the answer to is as quick as it ever was. **A search is a third disclosure** — the question reaches a search provider as well as Anthropic — and it is in the Settings row, the guide and the privacy policy like the other two.
- **Only the run of text after the last non-text block is the answers.** A searched turn holds what the model said before it looked anything up, the search, what came back, and then the answer; joining every text block would draw "let me look that up" on the board as something to say. `MAX_TOKENS` has room for a search query because that is output too, and what keeps each answer short is the brief rather than the cap.
- **One answer to a line, and `readReplies` is forgiving about it.** A format a model cannot half-follow is worth more here than a strict one: no JSON to be truncated, no beta header, and a line that came back malformed costs its own line rather than the whole list. Numbering, bullets and quotation marks come off — the brief asking for none of them is not the same as never getting them, and all three end up spoken — the same answer twice is one answer, and twenty is the cap. Running out of tokens mid-list costs the last line rather than the lot.
- **Which model is a setting**, in the Suggested replies row and only once a key is set, since without one it would choose nothing. `REPLY_MODELS` is the list: the **first three ordered by how long they take**, because that is the axis that matters most here, and the fourth off that axis entirely — Fable is a different voice rather than a faster or a slower one, so it is last rather than slotted among them. The default is the quickest for the reason the ElevenLabs voice is Flash: this is somebody mid-conversation with a person waiting in front of them. A full screen of dwell tiles rather than a list that drops down, for the reason every choice in this app is one.
- **A closed list, checked in three places.** `readReplyModel` is asked by `loadSettings`, by a backup's `readSettings`, and once more by `suggestReply` itself. A model name is handed to somebody else's API, so a board opened in a later release and then in this one would otherwise fail **on the first question somebody was asked** rather than in the settings panel. The third check is the one that matters: it is the last point before the name becomes a request.
- **The key is the user's own.** Not a preference: a Google key can be pinned to one site by referrer, which is what makes the translation key safe to inline, and nothing restricts an Anthropic key that way. One shipped in this bundle would be one anybody could lift and spend. So there is a Settings row beside ElevenLabs, following every rule that key follows — **never in a backup**, and it **does travel in a snapshot**, three-stated so that silence from an older release is not read as a removal.
- **It is given the board, and told to use it for a third of the list.** Every phrase goes with the question, the emergency bar's included, and the brief asks for the best of them word for word — an answer off the board is in words the person chose, on a board they already know how to read. **The whole board rather than a few picked out**, because what makes a phrase the answer is what it means: "are you hungry?" shares no word with "I'd like something to eat", and a keyword preselection would only ever find the phrases a model needs least help finding. **A third rather than the lot**: told to offer the ones that answer the question, a model with two thousand phrases in front of it filled all twenty cells from the table — a board that size holds something loosely on topic for anything anybody ever asks, so the feature became a search of the board, and what somebody is missing when they are asked something is usually the words they have *not* got. So the brief names three sources — their phrases, answers the model writes in their voice, and answers out of what it looked up — and asks for them mixed through the list rather than grouped, since the first few cells are the ones a tired reader gets to. `FROM_BOARD_CAP` enforces the third in `mixed`, because a brief is a request: the overflow off the board is **dropped rather than reordered**, best-first being the model's judgement and there being nothing here to put in its place, so a list that ignores the brief is drawn shorter and says so. Six things about it:
  - **What they can say, not what is true of them.** The rule about whose facts lets the model state what "is in what you were sent", and a board holding "I'm in pain" was sent. So the brief names the phrases as the opposite of evidence, in as many words, and holds a phrase stating something about them to the rule a sentence of the model's own would be held to. `tests/listen/suggest.test.ts` asserts the line.
  - **Written the way a reply's gap is written.** `boardForReply` turns a slot with a choice in it into `___` — which choice is theirs to make, and usually the fact the model is kept from stating — and a slot with one option into that word, which is how the board reads it. So a phrase chosen off it lands with the caret in its gap exactly as one off the grid does. The markup comes off with the slots held by a private-use character, or two gaps with a word between them read as emphasis. A phrase that is only a link is left out, and each wording goes once.
  - **Cached for an hour.** About thirteen thousand tokens on a board nobody has added to, and identical from one question to the next, so it is the one block carrying `cache_control` and nothing that changes between questions sits in it or ahead of it — the date comes after it and the question is in the messages. An hour rather than the default five minutes because a care room is not a chat: a question, twenty minutes of nothing, then whoever comes through the door next. Every model on the list has a cacheable minimum well under the board.
  - **In the board's order, never the grid's.** `talk.tsx` hands over `mainPhrases` and `emergencyPhrases`, not what the grid is showing: under Most used that moves every time a phrase is said, which would write the cache again on nearly every question — and it would carry how often each phrase is used, the one record under *What Peri stores* that goes nowhere at all. `tests/app/listen.test.tsx` uses a phrase between two questions and holds the two boards equal.
  - **It is a disclosure**, and the three documents say so: the Suggested replies row, *Getting suggested answers* in the guide, and the Listening section of the privacy policy — which also names the day's earlier questions, since they go too and the policy used to say nothing but the question did.
- **The question the model is given is the meaning where there is one and the heard words otherwise.** A model reading a question in the language it was asked in answers it just as well; the translation is there for the user rather than for the model.
- **A question that settles with nothing in the message box answers itself.** The dwell it saves is the point: somebody has just been spoken to with a person waiting in front of them, and aiming at a button before the machine will even begin thinking spends the seconds this exists to give back. **On the recogniser stopping rather than on a final result** — that is the one moment the whole of what was asked is in hand, a final result part-way through being half a question. Nothing is asked after a failure, there being no question there but only a reason there is not one, and nothing is asked while there are words in the box, a message half written being how somebody says they are already answering. The control stays for clearing the box and asking again, or correcting the question first. `messageEmpty` is one value handed to the hook and back out again, so the control and the automatic asking cannot disagree — and **edit mode counts as not empty**, the board there being a set of phrases to open rather than to say.
- **The board the answers are coming to says so.** `.grid-empty.is-busy` is the tab's own empty line with a spinner on it, which is why the tab appears while the question is still out: the seconds between being spoken to and words appearing are seconds in which nothing has happened as far as the person can tell, and a gaze already on the board should not have to go looking for the news that cells are coming. It is the one thing in this app that waits somewhere other than the corner. It does not wait the usual quarter-second, unlike every other indicator here: there is nothing behind it to flicker against, the tab is empty until the answers land either way. `Heard.asking` is `'' | 'meaning' | 'reply'` rather than a flag each, since only the answers land somewhere else. Never a target — `pointer-events: none`, like every other indicator here. It stood in the message box while a reply landed there; nothing arrives in the box by itself any more, so a line there would have been pointing at the wrong place.
- **A gap, not a question back.** What the model may not state about the person it leaves a hole in, written `___`, and the hole becomes the app's own `BLANK` with the caret landing in it — the same landing a fill-in-the-blank phrase off the board gets. Asking "which tablets?" would be a machine interviewing somebody who is already having to spell their answers out one letter at a time. Two or more underscores are taken, because a model asked for three will sometimes write two or four and a reply with visible underscores is worse than a gap a character too wide; **a lone underscore is left alone**, being a character somebody's name might have in it.
- **Today's questions and replies go back with the next one**, as the turns they were: "tea or coffee?" followed by "milk?" is one exchange, and a reply to the second that had never seen the first would be answering a different question. `loadReplyContext` is the record and **it expires after a day** — a carer's shift, a hospital visit, an afternoon — pruned on the way *out* as well as in, so a board left open overnight forgets on its own rather than waiting for the next question to notice. Twenty exchanges at most, since every one of them is sent again and paid for in tokens and in the seconds somebody is waiting.
- **The conversation follows the Sent list's rules**: its own key — two now, the turns and the answers last offered — never in a backup, never in a snapshot, cleared by a factory reset, and taken away with the key it belongs to. It is a record of what somebody was actually asked in a care room, so there is also a control in the Settings row for the person who wants it gone now rather than in the morning.

### Filling the silence

**Three seconds is a long silence with somebody standing in front of you.** A reply can take several, and the person using the board cannot fill that — filling it is what they came here for. So the board fills it for them: one short apology, said aloud, once a question, while the answers are still coming.

- **It is the board's sentence, not theirs.** Said through `speak` and recorded nowhere: not in the Sent list, not counted towards any phrase, not in the conversation the next reply is written against. The whole app is arranged so that nothing says anything as the user; this is the one thing the board says as *itself*, which is exactly why it apologises for the wait and says nothing else.
- **`instant`, for the reason the emergency bar has it.** This fills a wait, so it cannot start one of its own: no fetching a voice, no translating.
- **Never the same words twice within the hour.** A machine that says the same sentence every time is a machine somebody is listening to rather than a person they are talking to, and the apology stops being an apology. `Apologies.said` is what remembers, and it is forgotten an hour later. Where everything has been said within the hour the one said longest ago comes round again — a repeat beats the silence this exists to fill.
- **Five are kept ready, and the shipped ones are behind them.** The failure it covers is a wait, so it cannot be fetched during one. `SHIPPED_APOLOGIES` answers with no key, with no network, on a board that has never waited, and whenever a request came back with nothing.
- **Topped up after one is said, and at no other time.** A board that never waits on an answer never asks for any. A fill that comes back empty is not tried again for ten minutes, so a board with no network asks once rather than once a question.
- **The request carries nothing of theirs** — no question, no phrase off the board, no conversation — which is what makes it safe to ask for at a moment nobody is being answered. It is the quickest model whatever the board is set to: five short sentences nobody reads, against a setting that is about the answers somebody will actually say.
- **Three documents say so**, as everything sent anywhere does: the Suggested replies row in Settings, *Getting suggested answers* in the guide, and the Listening section of the privacy policy.

**Two disclosures, not one**, and both follow the rule the ElevenLabs key follows — the Settings row, the guide section and the privacy policy all say the same thing. The microphone's audio goes to the browser's own speech service, which is the platform's business and not Peri's. The question goes to Anthropic, on the user's own account, only when they ask for a reply.

**A key in a public bundle is safe by restriction, not by secrecy.** HTTP referrer to this site, API restriction to Cloud Translation alone — so what a lifted key costs is quota rather than anybody's words. `docs/translation-setup.md` is the whole of it. Three consequences worth knowing:

- **`hasTranslateKey()` is asked before the async path starts**, not left to the client to refuse. With no key the words have to go out **in the same tick**; a promise resolving into the original a moment later is a phrase that arrives after it was needed.
- **`GOOGLE_TRANSLATE_KEY` and `VITE_GOOGLE_TRANSLATE_KEY` are different keys.** A referrer restriction is what makes the app's safe to ship, and a referrer is exactly what Node does not send — so `pnpm translate` gets a 403 from it and takes an unrestricted one off the command line instead.
- **Tests run with no key unless one is stubbed in.** Vitest loads `.env.local`, so `tests/setup.ts` clears the variable for every test: without that, a machine with a real key runs different tests from CI, and the ones that matter most are about there being no key.

Sending the words somewhere is a disclosure, so it is stated in three places that must agree: the note on the **Spoken language** row in Settings — which is where it moved when there stopped being a Translation row to put it on — the **Speaking another language** section of the guide, and the Speech section of the privacy policy. Change one and change all three — the same rule the ElevenLabs disclosure follows.

## Backups

A backup is a **diff against the phrase table, not a copy of it**. The table ships with the app, so a file holds only what the user did — added, reworded, moved, removed, rearranged — plus their details and settings. That is why ids matter: they hash the source text, so an id in a backup still names the same phrase in a later release, and one that names nothing is skipped.

Two things in `src/backup.ts` are deliberate and easy to "fix" by mistake:

- **Merging never removes a phrase.** Deleting a phrase is the one change the app offers no way back from, so a file someone else made cannot make one on your device. Only *replace* applies removals, and `canReplace` refuses it for a file covering a few categories — everything the file said nothing about would go.
- **Imported settings are clamped to `SETTING_LIMITS`.** A dwell time of zero fires every control the instant a pointer crosses it, leaving a gaze user no working control to undo it with — and a `repeatDelayMs` of nought empties a list before it can be read, with the control that would slow it down repeating just as fast. A file does not get to set a value the settings panel could not. `readSettings` builds the object field by field, so a new setting is a compiler error here rather than a silently dropped one.
- **Merging aliases adds and never takes away**, for the reason merging phrases does: a file somebody else made must not be able to delete a word off a list on your device. A list in both keeps this device's words and gains the file's; only *replace* takes the file's wholesale.
- **`emergencyOrder` travels with the Emergency category and is never filtered down.** The other lists in a file are trimmed to the categories in scope; an arrangement trimmed to a few of its own ids is not a smaller arrangement, it is a wrong one. Merging appends what the file arranged behind what this device already had, exactly as `categoryOrder` does, so a file cannot rearrange a bar underneath the person using it.

## The board as a spreadsheet

**Menu → Backup & sharing** also hands the whole board out as a spreadsheet and takes one back. A backup is a diff for putting a device back the way it was; this is the other thing people ask for — **every phrase as a row somebody can read and edit** in Excel or Google Sheets, where writing two hundred phrases is an afternoon's typing for whoever helps somebody set up their board rather than a week of it by dwell. `core/sheet.ts` is the format and the rules, `core/xlsx.ts` the workbook, `menu/sheet-section.tsx` the screen.

- **One row a phrase: Category, Phrase, ID.** The emergency bar first, being the part somebody reaches for without reading, then the tabs in the order they are shown, each in its own arrangement.
- **The phrase is its source**, slots and markup and all, so a row read back is the phrase it was rather than the words one choice of its slots showed.
- **The ID is what makes the sheet an editor rather than a list**, and it is written with a `#` in front. Phrase ids are short base-36 hashes, and a spreadsheet opening `12e45` reads a number in scientific notation and writes it back as something else; the mark makes every one of them text to every program there is.
- **Three ways out, because three programs are asked for and want different things.** Excel wants a workbook: it reads a CSV by guessing, and guesses that `1/2` is the second of January, while a workbook's `inlineStr` cells say they are text. Everything else takes CSV. **Google Sheets takes a paste** — tab-separated text pasted into an empty sheet puts every phrase in its own cell, with nothing uploaded anywhere — and the way back is copying the cells and resting on *Paste from Sheets*. A real Google account integration was considered and not built: it needs the Sheets and Drive APIs switched on and a consent popup on every use, which a browser blocks on a pure dwell.
- **An apostrophe guards what a spreadsheet would rewrite.** Formulas in every format, because a board is a file people hand to each other and a cell opening as `=HYPERLINK(…)` runs whatever it says — and a markdown bullet begins with `-`, which Excel shows as an error. **Number-like cells only in the paste**: opening a CSV, Excel shows the apostrophe rather than obeying it, while a paste obeys it and hides it. Taken off on the way in, **and only in front of something it could have been guarding**, so "'Tis the season" keeps its own.
- **The CSV carries a byte-order mark**, or Excel reads it in the machine's code page and every accent comes out as two wrong characters. **Reading, the encoding is found rather than assumed**: UTF-8 strictly, then Windows-1252 — Excel's "CSV (Comma delimited)" is not UTF-8 — and UTF-16 behind a byte-order mark, which is Excel's "Unicode Text". A NUL byte anywhere else is a file that is not text, refused rather than offered as a thousand phrases of noise.
- **A paste is read as tab-separated, never guessed at.** Every spreadsheet puts tabs on the clipboard, and a single column of phrases guessed at would be split at its commas. A file is guessed at, among tab, semicolon and comma — Excel writes semicolons wherever the decimal point is a comma.
- **Headed, columns are found by name** in any order and by the names a person would give them; **unheaded, they are Peri's order**, and a single column is phrases.
- **What a row does, first rule that matches**: an ID on the board takes the row's wording and category; an ID for a phrase taken off the board brings it back; the same wording in the same category — matched as the editor matches, `phraseKey`, now in `core/store.ts` for both — is that phrase and adds nothing, so a sheet read twice does not double the board; anything else is new, under Imported where the row names no category. Categories match regardless of case. **Nothing moves onto or off the emergency bar unless somebody wrote it**: the bar Peri ships is a fixed six, so a sheet filing one under Greetings is a wording change and no more.
- **The word lists ride after the phrases**, one word a row, filed under the list's name **in curly brackets** — `{contacts}`, the way a phrase names it — with no ID. The missing ID is what makes the brackets safe: every phrase row Peri writes has one, so a category somebody did name in brackets comes back as a category. **A list with no words is a row with an empty phrase**, or the two lists Peri ships empty would be missing from the sheet and replacing would take them away. `aliasNames` and `aliasWords` in `core/phrases.ts` are what the Aliases panel and the sheet both ask, so the two cannot disagree about which lists exist. Six rules, in `applyLists`:
  - **A list is found by the name a phrase would find it by** — its own, then with an `s` on or off — so `{contact}` typed into a sheet is the `contacts` list, which is what a phrase writing `{contact}` gets.
  - **A word already on a list, in any case, is that word**, and takes the sheet's spelling. A list has no IDs, so a word is its own.
  - **A list taken off comes back as the sheet has it**, and where that is exactly the table's it is un-hidden and nothing is written, so it follows the table into the next release.
  - **The order of the rows is not read**, for lists as for phrases. What the sheet adds goes on the end.
  - **Replacing takes lists away only where the sheet has any.** A sheet with no lists in it says nothing about them, and the button says *Replace all phrases* rather than *Replace phrases and lists*, so it does not claim to do what it will not.
  - **Names come from a spreadsheet now**, so every read of a list is an own-property read (`hasList`): `lists.constructor` on a plain object is a function, and a sheet naming `{constructor}` must get a list.
- **Add and update never takes anything away**, the rule a backup's merge follows. **Replace phrases and lists** makes the board match the sheet — deleting what somebody wrote, hiding what Peri shipped, the bin's rule — and is offered only for a sheet with an ID column and only when it would remove something — phrases, lists or words — **saying how many first** (`describeRemovals`). A row that lost its ID but kept its wording is still that phrase, and replacing does not take it away.
- **The plan is counted when the sheet is read and applied against the board as it is when somebody confirms.** The count is what they agreed to; the store it lands on has to be the current one.
- **The workbook is written by hand.** A board is three columns of text, so writing one is a few XML templates in a zip with nothing compressed, and reading one is finding the first sheet — **the tab on the left, by the workbook's own order**, not whichever file is called `sheet1` — and its strings. The library that does all of Excel is several hundred kilobytes, and the one most people reach for stopped publishing fixes to npm. Checked by more than its own tests: a workbook it wrote opens in openpyxl with warnings as errors, and the fixture it reads came out of openpyxl. **It has not been opened in Excel itself here**; that is worth doing once on a real machine.
- **`FileButton` is the one file chooser**, used by the backup and the spreadsheet alike, so the rule that a rest cannot open a picker — and must say so, naming the paste that works — is written once. `tests/app/structure.test.ts` holds the one bare input in the app to being there and being hidden.
- **Nothing here leaves the device.** A file goes where the browser saves files and a copy is the clipboard, so there is no disclosure to make; the guide says as much.

## The emergency bar

The blue bar is the one surface somebody reaches for without reading it, so which button sits where is theirs to set. **It is not red**, and `--urgent` is not `--danger`: red in this app means destruction — delete a phrase, empty the board, sign out — and a red bar along the bottom said *careful* where it needed to say *here, now*. **Menu → edit mode → the arrows at the end of the bar** turns reordering on; from there it behaves exactly like the category tabs, and both come out of `ui/reorder`.

- **The order is by phrase id, and empty means the order Peri ships.** Ids, so rewording a phrase leaves it exactly where it was put — the whole point of arranging a bar is reaching it without looking. Unlike the categories there is no second arrangement to switch back to: the shipped order is the order they happen to be written in, and nobody is looking for it back.
- **A phrase added later lands at the end.** `orderEmergency` ranks the ids it knows and leaves the rest as they came, so adding an emergency phrase does not rewrite an arrangement, and an id naming a deleted phrase is skipped rather than leaving a hole.
- **Reordering is its own mode, separate from the category tabs'.** One flag for both would arm the bar somebody speaks with every time they set about tidying their tabs. Both are modes *within* edit mode, and leaving edit mode disarms both.
- **The add control goes quiet rather than away while reordering.** Adding a phrase mid-reorder would drop whatever is in the air, and moving a control a user has learnt to find is worse than disabling it — so the two tools keep a constant width either way.

## Sent messages

Every message spoken or copied is kept, newest first, and shown under a **Sent** tab pinned to the left of **All**. Selecting one puts it back in the message box; in edit mode it comes into the box to be *kept* as a real phrase, and the bin *forgets* it.

- **Sent is not a category.** Its filter id is `SENT_FILTER`, which begins with a space so no real category — names are trimmed — can ever collide with it. Both it and All carry `fixed: true` in the `categories` prop, which is how `FilterBar` knows a tab cannot be renamed, dragged or reordered.
- **The list is never in a backup.** It is a record of what somebody actually said, and a backup is a file made to be handed to somebody else. Its own storage key, outside the three things `buildBackup` reads, with a test holding it there.
- **The order on screen is the order the tab was opened in.** The record moves as it always did — `addSent` puts a message said again at the front — and what is drawn holds until somebody looks somewhere else, the same rule the board follows under an order that goes by use. See *Ordering the grid*.
- **`record` and `forget` read storage back rather than closing over state.** Two sends can happen without a render in between, and the second would otherwise be written against a list that no longer exists.

## Voices

Two sources sit behind `speak()`. The device's own synthesiser is instant, free and works offline. A linked ElevenLabs account sounds better and does none of those things. Everything in `src/speech.ts` is arranged around one rule:

**A phrase never fails into silence.** A flat connection, an expired key, a rate limit, a browser refusing to autoplay — every one of them ends in the device speaking the words instead. If you add a path that can produce no audio, it falls back too.

Two consequences worth knowing before changing any of it:

- **The emergency bar never waits on the network**, via `speak(text, settings, { instant: true })`. That is not the same as "device voice": a phrase given its own voice keeps it there too, because assigning one fetches and stores the audio, so it is already in hand. What `instant` rules out is *going and asking* — anything not already fetched is said by the device this moment rather than in the right voice a second and a half later.
- **A new phrase starts from the last category and voice used**, kept under `peri_recent` and out of backups — it is where somebody had got to, not anything they made. Only a *starting point*: a phrase that already has a category or a voice shows its own, so opening one to fix a typo cannot quietly refile it or change how it sounds. A remembered category that has since gone is ignored, and unlinking an account forgets a remembered voice from it. **Opening edit mode on a category writes that category there too** — see *Editing a phrase*.
- **A phrase can carry its own voice**, in `voiceOverrides`. It beats the one in settings wherever the phrase is spoken, and it travels in a backup like any other customization. A phrase written from nothing has no id until it is saved, so `addPhrase` **hands its id back** and the voice is hung on it afterwards — the choice was simply dropped before, and the phrase came out in the app's voice however carefully another had been picked.
- **The API key is never in a backup, and does travel in a sync snapshot.** Two different questions with two different answers. A backup is a file made to be handed to somebody else, and the key in one hands over the account — it lives under its own storage key, outside the three things `buildBackup` is built from, and `tests/core/backup.test.ts` holds it there. A snapshot is sealed with the user's own passphrase and reaches their own devices and nowhere else, so the key rides **beside** the backup in `Snapshot.account` rather than in it. Put it inside the backup and every exported file would carry it too. `src/legal/legal.ts` says both halves to the user.

Audio is cached in two layers by `voice/audio-cache.ts`. The memory layer answers synchronously, which is the only kind of answer the emergency bar can use; the IndexedDB layer exists so the memory layer can be full again after a reload, and `useBoard` pulls the assigned phrases back into it at start-up. Where IndexedDB is missing — an old browser, a private window, jsdom — everything still works and simply forgets between sessions.

Audio is cached in memory by voice and text. An AAC board is the same phrases over and over, so the second time is free and instant — which is the difference between a usable feature and a bill.

### Not paying for a clip twice

A clip is billed per character and is decided entirely by the voice and the words, so the same phrase is the same bytes for ever and on every device. **Four places are asked before ElevenLabs is**, in the order they cost least, and `fetchAudio` in `voice/elevenlabs.ts` is the whole of the chain:

- **Memory**, synchronously. The only question the emergency bar asks, and the only one that can be answered in time to matter.
- **IndexedDB**, on the way to the network rather than at start-up. **This was missing for the whole life of the feature**: every clip fetched was written there and nothing ever read one back except the handful of phrases carrying their own voice, so a reload bought the entire board again, one phrase at a time, with the audio already on disk. A board's worth read back on arrival is work nobody asked for, so the few clips that must be in hand *before* they are wanted are still warmed by name in `use-board.ts` and everything else is reached at the moment it is asked for.
- **The user's own other devices**, `sync/audio.ts`, when synchronizing is on. Absent otherwise, which is how the app ships.
- **ElevenLabs**, and what comes back is offered straight back up the chain so that no device on the account pays for it again.

Every layer fails into the next rather than throwing: a refused database, an unreachable server and a wrong passphrase all cost a clip somebody already owned, never a phrase.

**`voice/` and `sync/` are the same line of the layering, so neither may import the other.** The cache takes a `RemoteClips` that something above installs, and the only thing that can see both is `talk.tsx` — which is why one `useEffect` there hands the sync control's `clips` to `setRemoteClips`. It hands back `null` on the way out, or a signed-out screen would leave a stale set of keys installed in a module.

Four things about what is on the server:

- **A clip is its own blob, and never part of the board.** The board is written whole on every change, and audio is bought by *speaking* rather than by editing — folded in, saying a new phrase would look like an edit to every other device and push a board nobody changed.
- **The address is derived from the cache key**, through the same HKDF the board's address comes out of — `clipAddress` in `core/crypto.ts`. So a second device works out where a clip is from the phrase already on its board, with nothing to look up, and the server is handed a different 256-bit number for every clip and can tell nothing from any of them. Working one backwards means already holding the passphrase, and anyone holding that can read the board itself.
- **What *is* listed is what has been uploaded**, in one more blob beside them, and it exists for exactly one reason: *Stop and erase the copy* has to take the audio too, and an address nobody wrote down is an address nobody can delete. So the index is written **before** the clip it names, and the invariant runs one way only — the list may name a clip that is not there, which costs a wasted DELETE, while a clip the list does not name would be somebody's words left on a server after they asked for them back. A clip the index cannot be written for stays at home.
- **A clip too large to send stays at home too.** `MAX_CLIP_BYTES` leaves room for what an envelope does to it: base64 to make it JSON, then the ciphertext base64 again, about eight fifths in total. It is around half a minute of speech, and a board phrase is a sentence.

Two costs, both deliberate and both worth knowing:

- **A miss now waits on one more request.** Asking the server happens *before* ElevenLabs, so the first time a phrase is said on a device it pays a round trip it did not used to. Only on a genuine miss, and **never on the emergency bar** — `instant` returns before `synthesize` is reached at all, which is what keeps that surface off every one of these paths.
- **The index is rewritten whole each time it grows.** It is a list of cache keys, so it is bounded by the size of the board rather than by how long somebody has been talking, and it is only written when a genuinely new clip is bought. Uploading it is not waited on, so it costs bandwidth rather than time.

The disclosure rule applies to this as it does to the key: the **ElevenLabs row** and the **Synchronize row** in Settings, **Better voices** and **Keeping two devices the same** in the guide, and the **Speech** and **Synchronizing** sections of the privacy policy all say that the audio travels and that erasing the copy takes it.

**A language is what speaks when nothing more specific has been said.** `settings.language` sets `utterance.lang`; a chosen voice carries its own and wins, because choosing a voice is the more specific thing to have done. Its real work is the case where the voice does not apply: **a `voiceURI` is a platform string and it travels between devices**, so a board set up on a Mac arrives on a phone naming a voice that does not exist there — and without a language that falls all the way back to whatever the *system* speaks, which is how an English board ends up read aloud in another language entirely. Three consequences:

- **The languages offered are the ones the device can speak *or* Peri can translate into.** That rule was once only the first half, on the grounds that offering a language with no voice is offering silence — which is true of a language with nothing behind it and false of one Peri ships a table for. No device has a Puerto Rican or a Patois voice, and both of those are the point, so `VARIETIES` leads the list and the device's own languages follow.
- **A voice is remembered for each language, and so is a phrase's own.** A voice *is* a language, so switching the board between two of them used to let go of the old voice and leave the browser to pick — which made choosing one a thing to redo rather than a thing to set, twice a day for anybody working in two languages. `settings.voicesByLanguage` and `PhraseStore.voiceOverrides` (now id → language → voice) are the two halves, and `chooseVoice`/`chooseLanguage` in `core/store.ts` are the whole of the arithmetic. Four things about them:
  - **The lookup is exact, and never falls back to another language.** A phrase given an English voice has not been given a Spanish one, and an English synthesiser reading Spanish is worse than the board's own voice, which is what nothing means.
  - **`''` is a key like any other** — the board following the device is a setting somebody chose a voice under too. It is also where a store or a backup written before any of this existed reads its single voice, since that is very nearly always the language it was picked in.
  - **`chooseLanguage` writes down the voice it is *leaving*.** A device restored from a backup written before this has a `voiceURI` and an empty map, and without that the first switch away throws the voice away — the exact loss the feature exists to stop.
  - **Where nothing is remembered the old rule still stands:** a device voice that does not match is let go of, and the browser picks one in the chosen language. An ElevenLabs voice is left alone — it has no language of its own and speaks whatever it is given, and is not in the device's list at all, which is what carries it past the check rather than any special case naming it.
- **The language and the voice are also at the message box's upper-right corner**, on a screen wide enough, riding the same border the modes ride at its middle. Four things about that strip:
  - **Their faces are the values** — the tag itself, `en-US`, and the voice's bare name — rather than glyphs naming the subject. A globe says which grid opens; `es-PR` says what the board will do. Six rem each, ellipsis past that, and the whole of it on the control's `aria-label`.
  - **It is positioned against the box, not the bar.** `.text-display-wrap` exists only for that: everything else here centres on `.topbar`, which is 4px off the box's true centre and invisible, but a *corner* found that way would be out by the whole width of the action rail.
  - **It is its own strip, never the modes'.** That one is the three modes, found by position without being read, and `tests/app/App.test.tsx` asserts it holds exactly three — nothing may be inserted into it.
  - **Whether there is room is a `matchMedia` check in `topbar.tsx`**, not a `display: none`, so the breakpoint is written once — and because each picker builds the device's voice list, which is real work to do on a phone that never shows them.
- **It changes nothing for ElevenLabs.** `eleven_flash_v2_5` reads the language off the text, and for a board the text *is* the language — the phrases are written in it. Forcing a `language_code` could only make a mismatch sound worse, and it would have to join the audio cache key, so changing the setting would quietly throw away a board's worth of audio somebody had paid for.

The voice picker opens on the chosen language where there is one and it has voices here — sixty voices in languages nobody will choose is what the chips exist for. Only where that group is real: a language set on another device may have nothing behind it on this one, and a filter showing an empty grid reads as a fault.

Sending the words somewhere is a disclosure, so it is stated in three places that must agree: the ElevenLabs row in Settings, the **Better voices** section of the guide, and the Speech section of the privacy policy. Change one and change all three.

## The phrase grid

The grid is the app's heaviest surface — up to two and a half thousand cells, at roughly twenty microseconds each to create. Two things keep it usable, and they solve different halves of the problem:

- **`content-visibility: auto`** on `.phrase-cell` lets the browser skip layout and paint for cells scrolled out of view. That is the browser's half.
- **`core/virtual.ts`** limits how many cells React creates at all. Switching back to **All** cost ~95ms of pure reconciliation before it and ~12ms after.

The window **grows from the top and is never repositioned by arithmetic**. Rows are not a uniform height — a phrase long enough to wrap three times makes its whole row taller, and about one row in five does — so anything that multiplied a row height by an index would put the grid in the wrong place a fifth of the time. Rendering the first *n* in normal flow cannot.

Two properties hold it together, and both have mutation-tested guards:

- **The first render is a screenful, not the table.** Measuring needs something rendered to measure, so `FIRST_WINDOW` is what goes in before anything has been measured; the effect measures on the next tick and takes it from there. It mounted all two and a half thousand cells on the way to windowing them down until this existed — on every load, and in every test that opened the board.
- **Unmeasured still means all of them.** Where nothing can be measured at all — a grid that has not been laid out — it renders everything, which is exactly what it did before any of this existed. A phrase out of reach is worse than a slow grid.
- **It cannot strand a phrase.** `needsMore` asks for more within a screen's height of the bottom, and content shorter than the viewport is always within a screen of its own end. So a window too small keeps growing until the grid is scrollable, however far off the measurement was. `rendered >= total` is the only thing stopping that being an infinite loop — removing it hangs the test suite rather than failing it.

## Ordering the grid

Four arrangements, offered under every category tab: **the board's own order**, **A to Z**, **recently used** and **most used**. `core/sort.ts` is the arithmetic, `core/store.ts` keeps the record it reads, and one button at the top of the grid rail chooses between them.

- **The control is one icon button above the jump to the top**, outside the five that scroll, and it opens a full-screen picker. A cycling glyph would be worse than anywhere else in the app: four states behind one mark is three dwells and a guess to reach the one you want. It is the only thing in that rail that does not scroll, which is why it is marked off from the rest — this rail is aimed at rather than read.
- **The glyph says which order is on, and so does the name.** `A to Z` and the board's own order reuse the marks the category bar already sorts by, so a user learns one mark for each rather than two.
- **A usage order is taken when somebody changes what they are looking at**, not on the dwell that used a phrase. It followed use live for a while, which is what the order says on the tin and is unusable: the cell just chosen slid to the front, every other cell moved around it, and the next phrase somebody went looking for was not where they had left it. **The counting still happens on that dwell**; only the rearranging waits. `ranking` in `talk.tsx` is the copy the board is sorted by, adjusted during render — the rule for state that follows a prop — when the tab changes or the order does. Choosing an order applies it at once, because that is somebody asking for it while looking at the picker rather than at the board.
- **Nothing is lost by waiting.** A board that is being read is a board nobody wants moved; a tab arrived at is a board nobody has read yet. The order those counts make is what the next tab shows, however many phrases were chosen before it.
- **What still moves the board on the dwell that chose a phrase is composing**, which puts the phrase in the message box and narrows the grid to the word at the caret. That is what `holdDwellsUntilMoved` is for now, and it is asked for only there: auto-speak moves nothing. The pointer is somebody's gaze and it rests where it last fired, so the cell that lands underneath gets a `pointerenter` of its own — the browser's doing, not a mistake — and would start dwelling on nobody's instruction. A second of deafness is the wrong shape for this one: too long for somebody who has already looked away, and too short for a gaze that stays put. So it is **held until the pointer is aimed somewhere else**, which works because arming only ever happens on arrival: the cell that arrives is refused and stays refused until the pointer leaves it and enters something else. It clears on *movement* rather than on that exit, which is the same rule from the other side — a pointer cannot leave what it is on without moving — and is also the half that covers the case where nothing lands under the pointer at all, which would otherwise leave the guard up and swallow the next thing somebody deliberately aimed at. `MOVED_AWAY_PX` sits above gaze jitter and far below the width of a cell.
- **The render window keys on the list, not on the array.** `PhraseGrid` takes a `listKey` — the tab and the word being typed — because under a live order the phrase array is a new one on every utterance, and restarting the window each time would shrink the grid back to a screenful mid-conversation and take the view with it.
- **A tile marks an order and Done applies it** — see `ui/pending-choice.ts`. It closed on the first tile for a while, on the grounds that there is nothing to preview behind the scrim; but a rest is how somebody looks at a tile as well as how they pick one.
- **Closing the picker holds the dwells for a second, by Done or by Cancel**, the timed guard, the same one the menu takes on its way out and for the same reason: every cell on the board has just moved, and the pointer has not.
- **Arranging happens before the search ranks anything.** Filtering to a category cannot reorder and the ranking is a stable sort, so arranging first lets the chosen order decide ties within a rank band while a typed word still puts the best match first. The other way round, "ttyl" would find "Talk to you later" and then bury it.
- **With nothing arranged, Custom order is the same array, not a copy of it.** `orderByIds` hands back what it was given when the order is empty, which is what keeps a redundant re-render from looking like a different list.
- **A phrase nobody has used goes after every phrase somebody has**, in the order the board already had it. Ranking the unused among themselves would mean a board that has barely been used comes out shuffled, which is the opposite of what asking for this order means.
- **One order per tab, not one for the board**, keyed by the tab's filter id — a category's name, or `all`. The categories are not alike: a long reference list is worth having alphabetically, a short one worth having by what gets used, and a category somebody arranged by hand worth leaving as they arranged it, so a single setting makes each of those the wrong answer everywhere else. **Arriving at a tab brings back the order it was left in.** What pays for a control that means something different under every tab is that it says which order is on, in its glyph and in its name, so a tab sorted differently reads rather than mystifies.
- **Every tab starts on `DEFAULT_SORT`, which is Most used.** A board arrives with two and a half thousand phrases in whatever order a table happens to list them, and the phrase somebody wants next is nearly always one they have wanted before. Nothing is lost by starting there: a phrase nobody has used keeps the place the board gave it, so a board that has not been used yet looks exactly as it always did and sorts itself out as it is spoken. **The consequence is that the board is rearranged for somebody by the time they come back to a tab**, rather than under them while they are reading it.
- **Choosing the default *drops* the entry** rather than storing it, so a record that is all defaults is an empty one — the rule the phrase arrangements follow. It is a view rather than content, so it has its own small key and never travels; the *arrangement* a category holds is content and does travel. `loadAliasSort` is the same shape one question smaller.
- **All offers no Custom order.** A hand arrangement belongs to one category and All shows every category at once, so there is nothing for it to be an arrangement *of* — the tile would promise something nobody could build. `sortsFor(canArrange)` is what the picker draws, and `sortFor` reads a stored `custom` there as the default rather than leaving All in a state its own picker could not get back to. **That second half is the point**: hiding a tile that is also a tab's way home is how you strand somebody, and it is why the default had to move off `custom` at the same time.
- **`canArrange` answers both questions.** Whether a tab offers Custom order, and whether its phrases can be arranged by hand, are the same question asked twice — false for All and for Sent.
- **A single order written before there was one per tab lands on All.** It was chosen while looking at some tab, and All is the one the board opens on, so it goes there rather than being thrown away.
- **How much each phrase is used is never in a backup, and never in a snapshot.** It is a record of what somebody actually said and how often — which body part hurts, who they keep asking for — and a backup is a file made to be handed to somebody else. Its own key, outside the three things `buildBackup` reads, with a test holding it there. Keyed by phrase id, so it is bounded by the size of the board rather than by how long somebody has been talking, and a deleted phrase's count goes with it. **It is listed in the privacy policy** — under *What Peri stores*, which claims to be everything the app remembers, with a line saying it is the one item there that goes nowhere at all. There is no Settings row and no guide disclosure to match, because nothing is sent anywhere; the guide describes the feature instead.
- **Sent is not a category, so none of this reaches it.** It is a record in the order it happened, newest first, and that is the whole of what it is for. **What it does share is holding still**: saying a message again moves it to the front of the record, which on the tab it was said from is the cell just used sliding out from under the gaze that used it. `heldOrder` in `core/sort.ts` keeps the order the tab was opened in, with anything said since at the front — at the front rather than at the end, unlike `orderByIds`, because this list is newest first and something arriving is new. The control **goes quiet rather than away** while Sent is showing — a control that came and went would move the five below it — and its label says why. Choosing a message from it counts nothing: those ids name a message rather than a phrase, and would fill the record with ids that can never match anything and never fall out.
- **A use is counted where a phrase is *chosen***, in `handleSelectPhrase`, whatever it then does — speak, compose, or open a link. Edit mode never reaches there, because a cell opens the editor instead, so opening a phrase to fix a typo is not using it. The emergency bar is deliberately not counted: those phrases never appear in the grid, so a count of them could only be dead weight in the record.

### The mark on the last phrase said

The cell last chosen off the board keeps `.selected` and `aria-current` **until anything else fires** — a scroll, a tab, a mode, the menu.

- **It was a third of a second on a timer**, which stopped working once the board could rearrange itself on the dwell that rearranged it: a flash on a cell that is moving at the same moment. A mark that lasts is what says *that one, and it went there*.
- **It ends on the next dwell rather than on a clock**, because what it claims — this is the last thing you did — stops being true the moment anything else happens, and because a timer would take it away while somebody was still reading the board for it.
- **`onDwellActivation` fires before the control's own action**, which is the whole of why a phrase cell can clear the old mark and set its own in one breath rather than clearing the one it just set.
- **The cell takes a boolean, not the id.** `PhraseCell` is memoised over a couple of thousand cells, and `id === spokenId` is `false` for all but the two that change.
- **Edit mode and arranging mark nothing**, because neither reaches `onSelect` — a cell there is a phrase being opened or lifted, and nothing was said.

### Arranging a category by hand

The fourth surface that can be arranged, out of the same `ui/reorder` as the category tabs and the emergency bar: one dwell picks a phrase up, a second on another drops it there, and a mouse can drag instead. It is **edit mode only**, and its own mode within it — a third flag beside the other two, because arming the board somebody speaks with while they tidy their tabs is exactly what separate flags exist to prevent.

- **`PhraseStore.phraseOrder` is per category**, keyed by the category's shown name and valued by phrase ids. That is the unit somebody actually arranges, and one flat list would have to name every phrase in the table the first time anything moved. It is also why **All cannot be arranged** — its phrases come from every category at once, and ranking them against each other's arrangements would interleave orders that were never about one another. The control goes quiet there and on Sent, and says why.
- **Ids, so rewording a phrase leaves it where it was put**, and a phrase added later lands at the end rather than rewriting the arrangement — `orderByIds` ranks what it knows and leaves the rest as they came. That function is `orderEmergency` renamed: the bar is one category's worth of buttons and a category is one tab's worth of cells, and the arithmetic never cared which.
- **A move captures the order that was on screen** and makes it the user's own, then switches the grid to Custom order — the rule `reorderCategories` follows, for the same reason: a move applied to a hidden order would land somewhere they could not see, and an arrangement nobody is looking at is not an arrangement. So sorting A–Z and then moving a few is a way to build one.
- **The list handed to `reorderPhrases` is what is actually shown.** In edit mode that is the whole category, because `filterWord` is empty there — the guard that stops the board narrowing to a phrase being written is also what stops an arrangement capturing only the search results.
- **`reorder` is undefined unless the mode is on.** `propsFor` builds a fresh object per cell per render, and `PhraseCell` is memoised over a couple of thousand of them. The label map is built only while arranging for the same reason, and it is a map rather than a scan because every cell asks what is in the air.
- **It travels in a backup, trimmed to the categories in scope** — unlike the emergency bar's, which is one category's and so goes whole or not at all. Merging appends what the file arranged behind what the device already had, per category, the rule every merge here follows. A rename carries the arrangement to the new name, and a rename that collapses two categories appends the incoming one behind the one it joins.

## Versioning

**`package.json`'s `version` is Peri's version**, a semantic one, and it started at 1.0.0. `vite.config.ts` reads it into `__APP_VERSION__`, `core/version.ts` hands it out as `APP_VERSION`, and the menu shows it at 0.8rem beside the name at 1.3rem, centred on the top line of every screen the menu shows. Built in rather than fetched, so it is right on a device that is offline.

**Every pull request says what it does to the version**, as exactly one of the labels **major**, **minor** or **patch**, and the `version label` check keeps an unlabelled one off main. It is the one thing about a change that the diff cannot tell you:

- **Major** — something somebody relied on stops working: a backup or a synchronized board an older release cannot read, a feature taken away.
- **Minor** — anything new a person can see or do.
- **Patch** — everything else: a fix, a change of wording, tests or documentation alone.

**`pnpm release` writes the commit**, on the branch, as the last thing before it merges: it reads the label off the pull request, bumps `package.json` by it, and commits `Version 1.3.2` and nothing else. The number is no longer worked out in somebody's head, and the label was agreed when the pull request was opened.

**On the branch rather than on main.** A workflow committing it to main would have to be let past main's own ruleset, and the only thing a repository can grant that to is a personal access token with write access to main, sitting in its secrets for ever. This needs nothing of the sort, and the check that runs on the bump is the check that guards the merge.

**At the merge, not when the pull request is opened.** Two branches bumping from the same base would both claim the same number, and the second to land would conflict in `package.json` — so each is rebased onto main, bumped from whatever main says by then, and merged one at a time. `tests/app/shell.test.ts` holds the field to major.minor.patch, and `tests/tools/release.test.ts` holds the arithmetic.

## Checks, releases and publishing

Two GitHub workflows gate main, a third publishes, and a ruleset ties them to it. **Netlify used to be the gate** — its build command was `pnpm check && pnpm build` — which made every deploy preview eight to ten minutes long and was the only thing between a change and main.

- **`.github/workflows/ci.yml`** runs `pnpm check` on every pull request and on main, as the check named **`check`**. A pull request's runs replace each other as it is pushed to; main's are left alone, since each says whether what is on main now is sound.
- **`.github/workflows/version-label.yml`** is the check named **`version label`**: exactly one of the three labels, or the pull request does not merge.
- **The ruleset on main** requires both checks and a pull request, allows only a rebase merge, and refuses deletion and force pushes. **Nobody bypasses it**, which is why the version commit is made on the branch — see *Versioning*. There is no approval requirement: one person writes this app, and a review they give themselves is a rubber stamp.
- **Merging is `gh pr merge --auto --rebase`**, which merges the moment the checks pass rather than making somebody sit and watch them.
- **Every workflow's token is `contents: read`**, and the repository's default token permission is read as well — so a workflow that is one day given a secret cannot also rewrite the repository.
- **Publishing is separate, and stays a decision.** `.github/workflows/publish.yml` (`gh workflow run publish`, or the Actions tab) runs `tools/publish.ts`: it refuses a main that does not end in a release commit, waits for Netlify's build of that commit, publishes that one build, and then asks the site what it is serving. **Auto-publishing stays off** — people speak through this app, and a release reaches them when somebody decides it should.
- **The Netlify token lives in the repository secret `NETLIFY_AUTH_TOKEN`**, named by that workflow and nothing else. A laptop holding it would be a second place to lose it from.
- **A deploy preview is still built for every pull request**, and it is still the only place to see the app in a real browser at a real size — what changed is that it no longer decides whether anything can merge.
- **`README.md` says all of this to somebody who has not read this file**, and has the table of what lives where — the one Actions secret, the `VITE_*` variables that are public by the time they reach a browser, the unrestricted key that never leaves a command line, and the three that belong to the user and never leave their device. Change any of that and change it there too.

## Code quality

- Use double quotes for strings containing apostrophes (`"We're here to help"`), or escape them in single-quoted strings. An unescaped apostrophe in a single-quoted string breaks the build.
- Ensure JSX tags are closed and braces are balanced.
- `src/App.tsx` has the only default export. Everything else is named, so a rename is a compiler error rather than a silently different component.
- Export only what another module imports. A component with one caller stays private to its file.
- The phrase grid is memoised over a couple of thousand cells. A callback reaching it must not depend on a whole hook result — those are a fresh object every render, and the memo would never hold. Depend on the specific function instead; `deliverPhrase` in `src/talk.tsx` shows the shape.
